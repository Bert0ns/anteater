# Cribrum — Design Document

- **Status:** Draft
- **Last updated:** 2026-11-17

## 1. Problem

A phone accumulates thousands of photos and videos. Many have no lasting value: blurry shots, near-identical bursts, lower-resolution copies of the same photo, pictures of lecture slides or homework taken for a single moment, screenshots, and forwarded media. Messaging apps make it worse. WhatsApp alone keeps received, sent, and status media in several folders, some of them hidden from the gallery. Videos hold most of the space: on the maintainer's phone, 1,419 videos take 59.8 GB and all 9,568 images take 2.5 GB (#172).

Gallery apps are built for browsing, not for cleanup. They don't search the whole storage, and they can't tell a memory from clutter.

The app reviews images, and videos through the categories that have a video detector and through "Largest videos" (#387, #389). The scan finds videos and records them in the index (#383), reads their metadata (#384) and finds the exact duplicates among them (#389). Epic #172 brings in the rest, and each section below names the issue that builds its part.

## 2. Goals and non-goals

### Goals

- Find **every** photo and video on local storage, including folders hidden from the gallery.
- Detect photos and videos that are likely deletable, grouped into understandable categories.
- Make reviewing hundreds of candidates fast.
- Never delete anything without explicit confirmation, and keep every deletion reversible for a while.
- Keep the code modular, so detectors, media sources, and model runtimes can be swapped or added easily.

### Non-goals (for now)

- Cloud photo libraries (Google Photos and similar).
- Cloud-based classifiers.
- Audio, documents and other files. Cribrum cleans photos and videos, and the storage map shows only what it can clean (§8).
- Publication on the Play Store.
- iOS and desktop versions.
- Visual polish beyond a clean, functional UI.

## 3. Key decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | **Android first, native Kotlin + Jetpack Compose.** | The heavy work is platform-specific: file system access, permissions, background jobs, image decoding, on-device ML. Cross-platform frameworks (Flutter, React Native) would still need native modules for all of it, plus a bridge layer that is hard to debug. Compose Multiplatform keeps a desktop option open. |
| D2 | **Python lab as the reference implementation.** | Detectors are built and tuned in Python on real photos first, then ported to Kotlin. Golden test fixtures check that both implementations give the same results. |
| D3 | **On-device analysis only.** | Privacy, zero cost, works offline. Cloud classifiers were evaluated (cheap, roughly $1–2 per 10,000 images) and postponed. The architecture keeps them pluggable (see §7). |
| D4 | **Recall over precision.** | Missing a deletable image is worse than surfacing one the user wants to keep. Thresholds start low, any single detector can make an image a candidate, and protection signals only lower an image in the ordering, never remove it from the candidates. The user can raise the thresholds in the settings (§6.1), which trades recall for a shorter review. |
| D5 | **Photo and video age is not a deletion signal.** | An old photo or video may be old precisely because it survived earlier cleanups. The review state of each file replaces age (see §6.3). Videos come under the same rule, and their review order weighs size, not age (§6.6). |
| D6 | **Nothing is deleted without confirmation, and deletions go to a trash first, kept 30 days by default.** In the review, the main button with its counts ("Trash 45, keep 3") is the confirmation of a page: it applies the page at once, and the 30 day trash and the Undo snackbar make it reversible. Only a page that marks a favourite asks first, in a dialog (#321). Deleting for good, from the trash, always asks. | Mistakes must be recoverable. How long is a user setting. A dialog on every page repeated the button's numbers on a reversible action, cost a tap per page, and taught users to tap through dialogs, which made the one that matters, for a favourite, easier to miss. |
| D7 | **Personal, sideloaded distribution first.** | Allows the "All files access" permission (`MANAGE_EXTERNAL_STORAGE`) without Play Store review. |
| D8 | **Local photos and videos only.** | Cloud libraries need their own cleanup, but they are a separate, future problem (see §11). Videos came in because they hold most of the space on a phone (§1). Audio, documents and other files stay out (§2). |

## 4. Finding images and videos on Android

This section describes how the scan finds images, as built today. It finds videos the same way, and [Videos in the scan](#videos-in-the-scan), at the end of the section, says what differs.

Two layers:

1. **MediaStore**, Android's media index. It covers the gallery and `Android/media/com.whatsapp/WhatsApp/Media/...`. It does **not** index folders containing a `.nomedia` file, such as `WhatsApp Images/Sent`. That is exactly where clutter piles up unseen.
2. **Deep scan** with `MANAGE_EXTERNAL_STORAGE`: a file system walk of shared storage that finds every image file, `.nomedia` folders included. The deep scan skips `.trashed-*` files (the system trash, which MediaStore hides by default) and `.pending-*` files (still being written), in both the lab and the app. It also skips `Android/.Trash` at the root of each volume, which is Samsung Gallery's own recycle bin: those images are already deleted as far as the user is concerned, and moving them breaks the Gallery's restore. Images already indexed there leave the index at the next scan, like any file the scan no longer finds, except those in Cribrum's trash. Since Android 11, `Android/data` and `Android/obb` stay inaccessible even with this permission. The deep scan recognises an image by the head of the file, except a file the index already holds with the same path, size and mtime: it does not read its head again. The walk also remembers the files it sniffed and found to be neither images nor videos (the `not_images` table, with path, size and mtime), and does not read their head again either. On a phone most of the files the walk lists are not images, so without this every scan opens all of them. A file with a new size or mtime is sniffed again, whichever of the two lists held it, so a non-image that becomes an image with a new mtime is found at the next scan. Three cases get through that the head would decide differently: a non-image written over an image that kept its size and mtime, an image written over a non-image that kept its size and mtime, and a file the walk turned away that MediaStore lists all the same (a DNG, BMP or TIFF, which the head does not take), if MediaStore later drops it, for example because a `.nomedia` file appeared in its folder. MediaStore brings such a file in as an image, since it reads `not_images` for video rows only (below). The first and the third stay in the index until the size or mtime changes. The second stays out of it for as long. The app does not handle any of them. A change that lets the head accept more, such as a new format or HEIF brand, would leave every file of that kind already in `not_images` unfound, while a fresh install would find it, so that change must empty the table: a Room migration that runs `DELETE FROM not_images` on Android, a schema bump in the lab. Accepting videos was such a change (#383). The table has no version column. The walk reads the remembered files once, before it starts, and adds the ones it sniffs in batches of 300. It drops a remembered file it no longer finds only under a root it listed in full, like the index does for images, so the table does not grow without bound and an absent volume keeps its rows. The review reuses its ranking while the index version is the same. A write to `not_images` leaves that version alone, because no image changes with it. So does a delete that removes no row, such as a scan's forgetting of files, trashed rows or sticker analyses when there are none: a scan that changed nothing keeps the ranking. The walk records the files it finds in transactions of 300. A scan that stops partway leaves out the batch it was filling, and the next scan records those files again.

A pass forgets a file the scan no longer finds only when the file is under a volume the scan walked in full. A source reports the roots it listed, and a volume that is absent, such as a removed SD card, or a root with a folder that could not be listed is not walked: its rows keep their review state until a pass walks it again. MediaStore walks no folder, so it never makes a file gone, and it leaves out the same trash, pending files and folders as the deep scan. It runs after the deep scan and skips the paths the deep scan already yielded before it stats them: the deep scan's record of a file wins anyway, and on a phone that is most of what MediaStore lists. It reads `not_images` once per scan, for its video rows only (#387). MediaStore lists an audio-only `.mp4` as a video, and without a skip the file came back as a new unreviewed row at every scan, showed in "Largest videos" with no metadata, counted among the videos that wait and lost any keep at each cycle. So a video row whose path `not_images` holds with the same size and mtime has its 64 byte head read again, which is a few files, and is left out only when its major brand is an audio one (`M4A `, `M4B `, `M4P `, `F4A `). Any other video row is yielded, including a video whose brand the walk does not know (it is in the scan log as `unknownBrand`), which MediaStore catches by the MIME type it gave it. An image row is never skipped. MediaStore is how a DNG, BMP or TIFF reaches the index, since the walk turns those away and remembers them, and skipping them would lose a raw photo for good (D4).

Deep scan is the default (D7). The scanner merges both layers and identifies each file by its path, size, and modification time. A review decision follows the path, so a file that is moved or renamed is a gone row and a new one: it loses "keep" and is analyzed again, embedding included. Carrying the decision over would need a match by size, mtime and content hash inside the forget step, for a case that costs the user one more look at the image.

Indexing is incremental. The first pass processes every file, and later passes only process new or changed files. On Android, WorkManager runs a pass once a day at night while the phone charges, and whenever the user starts one with "Scan now". Opening the app starts no scan, since a pass keeps the CPU busy for minutes and the user who opens the app only wants to review. The first pass after install is the user's too: while the index is empty, the home screen says so and points to "Scan now" in one sentence that also says the first time takes about 15 to 20 minutes for 10,000 images, that the user can leave the app, and that Cribrum then scans again at night while the phone charges, unless the user turns that off in Settings (#329, #443), which explains counts that change and a trash that empties on its own. "Scan now" is a filled button until the first scan, outlined after it with the date and time the last scan ended beside it ("Last scan: Nov 4, 03:12"). The first scan here is the first that ran the image steps: a "Scan videos" records the images it walks past and analyses none, so once one has started, the Photos tab keeps the first-scan sentence until the image steps have finished once (`imagesAt` in the last scan's report, below). An install that never started "Scan videos", or whose report predates it, goes by the index alone. A pass already running keeps running when the app opens, and its progress shows, whether the nightly request or "Scan now" started it. "Scan now" is offered only while no pass runs. The daily request needs charging and a battery that is not low. WorkManager has no time-of-day constraint, so the first run is delayed to the next 02:00 local time. WorkManager measures each later run from the end of the previous one, so a night without charging would move the scan to the hour charging starts, say 14:00 at a desk, and every day after. Two rules keep the scan at night. The nightly worker scans only between 00:00 and 06:00, and outside that window it returns without scanning. When it ends, whether it scanned or skipped, it pins the next run to the following 02:00 (`setNextScheduleTimeOverride`). So a night without charging is skipped and the next 02:00 is set again. Only one scan runs at a time: a nightly run that starts while a "Scan now" pass is running returns without scanning. A "Scan now" waits for the lock instead (#321): right after "Stop scanning" the stopped pass can still hold it, and dropping the tap would leave the user with nothing happening. It still gives way to a compression batch that waits or runs, which holds the lock for the whole batch (§9). A scan does not run while a compression batch waits or runs either (§9). `setRequiresDeviceIdle` would also work, but it can hold a run back for days on a phone that is never idle while charging, and the delay is simple to test. A pass runs as a foreground service with a notification, since a first scan of thousands of images outlasts the few minutes Android gives background work. The notification has a "Stop scanning" action (#321), WorkManager's own cancel intent for the pass's work, as the compression batch has: the index keeps what the pass did, so the next scan resumes from there. The scan block on Clean has the same stop, a "Stop scanning" button under the progress (#329), so a scan can be stopped with notifications off too. It sends the same cancel (`Indexing.stop`, `cancelWorkById` on the running pass's request), so everything below holds for both, and a stopped "Scan now" leaves the nightly request as it was. Stopping the nightly pass cancels its periodic request, so the worker, stopped, schedules it again in its `finally` (`schedulePeriodic`). It uses KEEP, so it adds the request back only when it was really cancelled: a run stopped because the charger was unplugged leaves it enqueued, and this does nothing. If Android refuses to start the foreground service from the background (such as ForegroundServiceStartNotAllowedException on Android 12+), the worker logs the refusal and continues as a standard background job under JobScheduler constraints, relying on the index to resume where it left off on subsequent runs. The notification title names the phase the pass is in ("Looking for images", "Reading the images", "Analyzing the images", "Classifying the images", then "Finding duplicates and bursts" for the group detectors) behind its number ("Phase 3 of 5 · Analyzing the images"), and its text shows the count. The scan screen names the phase the same way, with the number on its own line above the title. Joined to the title, the Italian line runs past 60 characters and is likely to wrap on a narrow phone, and the list below would then jump at a phase change. The total is a fixed 5, one for each title, numbered in the order the phases run: the walk, the metadata, the detectors that read no embedding, the embeddings together with the detectors that read them, then the group detectors, which are all phase 5 even though each reports its own step. These five are the normal scan's. A video scan numbers only its own phases ([Videos in the scan](#videos-in-the-scan)). A rescan skips a phase that has no work, so the number can jump, from 2 to 5 for example. The embeddings and the detectors that read them (`DOCUMENT`, `FORWARDED`) are one phase, "Classifying the images", because they run at the same time (#357): the encoder runs on the GPU while the CPU only decodes for it, and the text coverage, the costly part of `DOCUMENT`, does not read the embedding, so each batch of embeddings goes to those detectors as soon as it is stored (§7). Two phases that overlap could not keep one number in the order the phases run, and two counts on one screen ask the user to follow two bars for one wait. Its count is in images: an image is done when the detectors that read its embedding have stored their results, or when it turns out to need none, such as one whose embedding failed. The images whose embedding an earlier scan stored go first, so a rescan that only has those to classify counts them as before. The time left follows the same 30 seconds, so it reads the slower rate while the encoder still takes two cores for its decodes, and drops a little once the embeddings are done. "Comparing the images", the title of the embeddings when they had a phase of their own, is gone. The total is not computed from what the pass will run, since that is not known when it starts. The number comes from the same mapping as the title, so the two cannot disagree. The phases follow the pipeline order in §7: the detectors that read no embedding run first, so the home screen has candidates after a few minutes instead of after the embeddings. The home screen reloads its list when a phase that can add candidates is over, so a user who watches the first scan sees them: after the walk (a trashed image put back by hand becomes unreviewed with its signals, and the first scan ends the empty index), after the detectors, after the classification (the embeddings and the detectors that read them), and when the scan ends, which covers the group detectors. The metadata and JPEG headers store no signal or review state, so the home does not reload after them (#356). Each reload reads the whole index and ranks it, 120 to 260 ms on the test phone, and it used to run at every step, about ten times a scan, competing with the scan for the CPU and the database. A phase the home did not see, because it ended between two progress reports, still counts, and the thresholds screen follows the same rule. The settings screen still reloads at every step, because the embeddings change its embedding count. The count it shows during a scan is the one at the start of the classification until that phase is over. A reload happens only while the home shows, so going back to the home reads it again, with the empty index and the last scan: a scan may have moved on or ended meanwhile. The home reads the index in a read-only transaction on one of SQLite's reader connections: one snapshot for the whole read, without the write lock that Room's `withTransaction` takes, so the scan's writes do not wait for it. The title changes as soon as the phase does. The count in the app updates at most five times a second, so the walk's count climbs instead of jumping, and the one in the notification at most once a second. Under the count, the home and the notification show the time left of the current phase, rounded to the minute ("About 12 min left in this step", "Less than a minute left in this step"). It is the phase's items left times its cost per item over the last 30 seconds, so a phone that slows down from heat, battery saver or another app raises it, and the 30 seconds keep it from jumping at each update. Nothing is carried from one phase to the next: it starts again at every phase, as the bar does, and the user sees how long the phase named above it needs, not the whole scan. An estimate of the whole scan was tried first (#242) and dropped (#271). It scaled the later phases by the current phase's live cost over a cost stored for it by the last scan, and a phase has no single cost per item, since the pipeline runs only the detectors an image is missing, so an item is one cheap detector or the whole set. A scan that repeated one cheap detector could store a tiny cost, and the next full scan would divide a normal live cost by it. That is the likely cause, read from the code and not measured, of the more than 8 hours the home once showed for a scan that took about 20 minutes. The price of the phase estimate is that the time can rise when a slower phase starts, and the user cannot read the length of the whole scan from it. There is no estimate during the walk, which has no total, nor for a group detector, which reports one item, nor in a phase before it has five seconds of samples; the line stays in place and is empty. The estimate is display only: it changes nothing the scan does, and costs a clock read and some arithmetic per progress report. The app also says when the phone is hot enough to slow the scan down, in one line under the progress with a thermometer icon: "The phone is hot, so the scan is slower", at the moderate and severe levels below, and nothing at the others (#321). It used to show every level with the headroom as a percentage ("moderate · 12%"), which a user cannot act on. The line comes last, so it never pushes the progress down when it appears. It reads the thermal status of `PowerManager` and its thermal headroom, and takes the worse of the two, because each covers a weakness of the other: some devices always report a status of none, and one headroom value can mean a different status on another model, while the headroom needs at least 10 seconds between reads and returns NaN otherwise. Headroom maps to a level with Google's scale (about 0.85 is light, 0.95 moderate, 1.0 and above severe); the status levels critical, emergency and shutdown count as severe, so there are four levels: normal, light, moderate, severe. A headroom that is not above 0 counts as no reading, and the last good one is kept, even across an unfold or a rotation, which recreate the activity, since a read soon after the last can return NaN on a phone that supports it. It is forgotten 10 seconds after a scan ends, so the next scan cannot open on an old reading. A listener and one loop, off the main thread and at most once every 10 seconds, run only while the home shows a running scan. The line only informs: it changes nothing the scan does, and the notification does not show it. Nobody has checked yet what a Galaxy reports for these two APIs. The index keeps what each pass did, so a stopped pass resumes where it was. The metadata and JPEG header phases read 4 to 8 files at once and one writer stores them, and the detector phases store their results the same way: 32 images in one transaction, instead of one commit or more per image (#358). A pass that stops loses at most the batch it was filling, plus the reads and analyses still running or waiting for the writer, and the next scan does them again. The reads run at most about three batches ahead of the writer, so a first scan of 10,000 images does not hold them all in memory.

### Videos in the scan

The scan finds and records videos (#383), and the pipeline reads their metadata when it is asked to analyse videos (#384). "Scan videos" and the night rule are built (#401), and so are the frames (#393) and the exact duplicates among videos (#389).

**What counts as a video.** MP4, MOV, 3GP, M4V, Matroska and WebM. The deep scan recognises a video by the head of the file, as it does an image, in the same first 64 bytes (`mediaType` in `MediaSource.kt`, `_media_type` in `sources.py`). An MP4, MOV, 3GP or M4V file has an `ftyp` box whose major brand is one of theirs (`isom`, `iso2` to `iso6`, `mp41`, `mp42`, `avc1`, `mmp4`, `XAVC`, `qt  `, `3gp4` to `3gp7`, `3g2a`, `M4V `, `M4VH`, `M4VP`). A Matroska or WebM file starts with the EBML header, followed by a DocType of `matroska` or `webm`. HEIF and AVIF images start with `ftyp` too, and an image brand anywhere in the box keeps them images, as before. Only the major brand counts for a video, because an `.m4a` (`M4A `), an audiobook (`M4B `), protected audio (`M4P `), Flash audio (`F4A `) and a Canon raw photo (`crx `) list `isom` among their compatible brands. So audio-only files with an audio brand stay out, and so do AVI and older formats. The head cannot see the tracks, so an audio-only file whose major brand is a video brand, or an audio-only Matroska or WebM file, counts as a video; reading more of it would break the rule below. The list decides, and a miss leaves a trace: the walk counts the `ftyp` and EBML files it turns away because it does not know their brand, by brand, in the scan log (`walk unknownContainers` and `walk unknownBrand '<brand>'` under `scan-time`, and the lab's `scan` prints them). The audio and raw photo brands above are known, so they are not counted. A file goes to `not_images` and is not sniffed again, so only the scan that first sniffs it counts it, which after the update is the first one. A GIF and an animated WebP stay images, and so does a Motion Photo (§9). The MediaStore source reads `MediaStore.Video` next to `MediaStore.Images`, and keeps a video only when the MIME type MediaStore gave it is one of those containers (`video/mp4`, `video/quicktime`, `video/3gpp`, `video/3gpp2`, `video/x-m4v`, `video/x-matroska`, `video/webm`), since MediaStore also lists AVI, WMV and others. It reads no file for that, as it reads none for an image, so it trusts MediaStore's type, which comes from the extension. The walk skips the same places for videos as for images: the Cribrum trash, `.trashed-*`, `.pending-*` and `Android/.Trash`. A video goes in the `images` table, with `media_type` set to `video` (§7). A file the index already holds keeps the media type it was recorded with, since its head is not read again. On the maintainer's phone MediaStore lists 677 of the 1,419 videos, and only the deep scan finds the other 742, almost all in `WhatsApp Video/Sent` (#383).

**The normal scan never opens a video.** "Scan now" and the night pass find and record videos, with their path, size, mtime and media type, and run no step on them. A video found by the walk counts in the walk's progress like any file, and no later phase counts it. Like any file the walk does not know, a video has its head read once, which tells the walk what the file is. That is all "never opens" means: no step of the normal scan reads more of a video, so it reads no metadata, no hash and no frame. A user who only cares about photos does not pay for the video steps, and those are the slow ones: reading 1,419 headers, then decoding frames of 4K HDR video.

**The metadata of a video.** A video step, which the pipeline runs only when it is asked to analyse videos: `videos` on `Pipeline.run` and on the lab's `pipeline.run`, off by default. Beside it, `images`, on by default, runs the image steps. "Scan videos" passes `images` off and `videos` on, and a night pass after it passes both on (below). The lab's `scan` takes `--videos` for both and `--only-videos` for the video steps alone, as "Scan videos" does. The step runs after every image step, the image group detectors included, in a phase of its own (`videoMetadata` in the scan log, `video_metadata` as the progress step). It reads the width and height after rotation, the duration, the frame rate, the bitrate, whether there is an audio track, the video codec, whether the video is HDR and the capture time (§7). The app reads them from the header with `MediaMetadataRetriever` and `MediaExtractor`, which decode no frame (`readVideoMetadata` in `VideoMetadata.kt`). The lab reads them with PyAV (`read_video_metadata` in `metadata.py`), and decodes the first frame for the rotation, since PyAV gives the display matrix only on a frame. When that frame does not decode, the lab logs the file, since a portrait clip then keeps its coded size there while the phone swaps it. The codec is stored as the MIME type `MediaFormat` gives it (`video/avc`, `video/hevc`, `video/x-vnd.on2.vp9`), and the lab maps FFmpeg's names to those. The bitrate is the file's size over its duration, in bits per second, computed by each side, since the two parsers count it differently. The frame rate is the number of frames the container counts over the video track's duration, rounded to two decimals: `METADATA_KEY_VIDEO_FRAME_COUNT` over the track's `KEY_DURATION` on the phone, `stream.frames` over the stream's duration in the lab. MediaFormat's own rate of an MP4 is an integer, 30 for a 29.97 fps clip, so neither side uses it while there is a count. A container that counts no frames, such as Matroska, gives the rate it declares instead (`KEY_FRAME_RATE` on the phone, FFmpeg's average rate in the lab), and there the two sides may differ: on the maintainer's phone the WebM fixture has no rate, where the lab reads 30. HDR means the transfer function is PQ or HLG. A video whose header does not read is marked unreadable, like an image, and keeps its row and its size. On the phone that is only what the native layer reports as a file it cannot parse (`IllegalArgumentException` from `setDataSource`): any other error is a failure of the step, and the next scan reads the file again. The phone also marks unreadable a file whose video track the retriever does not see. Android's extractors see only the codecs they know, so a ProRes or Motion JPEG MOV, or a Matroska file with a codec the phone lacks, reads as having no video track, and these are among the largest files a user has. Dropping them would lose them for good, against decision 17 of #382. The price is that an audio-only MP4 shows as an unreadable video. The lab asks FFmpeg, which knows those codecs, so a file that opens there with no video track is not a video: it leaves the index and goes to `not_images`, so the walk does not sniff it again until its size or mtime changes. The lab counts these files on their own, not among the files that are gone. The golden videos in `fixtures/videos/` hold what both sides must read: the lab's tests read them, and `VideoMetadataDeviceTest` reads them on a phone, since Robolectric has no media parser. `expected.json` lists the file the phone may read or mark unreadable (`prores.mov`), the file whose frame rate may differ (`clip.webm`), and the audio-only file the lab drops and the phone keeps as unreadable.

**The frames of a video (#393).** A video step after the metadata, in a phase of its own (`videoFrames` in the scan log, `video_frames` as the progress step, "Looking at the frames", phase 3 of the video scan). It needs the model, so the lab's `scan --no-embeddings` skips it. It takes each video whose metadata was read, readable and out of the trash (`readVideos`, `read_videos`), samples five frames, embeds each with MobileCLIP and stores the five vectors (§5, §7). The frames themselves are never stored, but each is measured while it is decoded, for the detectors that read frames (§5, #394): the measures go in the same transaction as its vector, so a video's frames and measures are always of one sampling. It works on one video at a time: the frames decode one after the other, the model takes them as one batch and the vectors are stored in one transaction, so the scan stops between two videos and a stop loses at most the video it was on. Each stored frame carries `FRAMES_VERSION` (`Frames.kt`, `frames.py`, compared by `check_parity.py`), which goes up whenever the frames a video gives change, in their times or their decoding, such as a switch to keyframes or another tone mapping (§5), or in what is kept of each frame (version 3 added the measures, #394). A video with a stored frame at a time the rule does not give now, with none stored, or with frames of another version, is sampled again, so the index never mixes frames taken two ways. An HDR video may keep fewer frames than the rule's times, one a keyframe (§5), so a missing time alone does not sample it again. The step finds them from the stored times alone (`sampledTimes`), without loading the vectors. A changed file loses its frames as it loses its metadata. A video whose frames do not read (a time with no frame, a blank frame on the phone, the retriever refusing the file, an FFmpeg error in the lab) is marked with the version it failed at (`frames_unreadable`), as an unreadable image is, and is not decoded again until the file or the version changes: a 4K clip that fails costs up to five decodes, which every scan would pay again. It is counted in the scan log (`video_frames unreadable`) and is not a failure, since another scan cannot help. A file that is gone by the time its frames are read, such as one the user trashed during the scan, is not marked. Any other error (out of memory, the model) is a failure of that video, shown as "Video frames" in Settings, and the next scan tries it again, as an image whose embedding fails. The scan log counts the videos the phase took (`video_frames tasks`) and the frames it embedded (`video_frames frames`). `VideoFramesDeviceTest` measures what one video costs on the phone. On a Galaxy Z Fold7 (Android 17, debug build), a keyframe of a 4K 60 fps HLG clip took about 90 ms to decode, 30 ms to copy and 78 ms to preprocess, and the model 55 ms a frame, so about 1.3 s for the video's five frames. An exact SDR frame took 100 to 530 ms to decode on 1080p and 4K camera clips and a WhatsApp video, against 30 to 150 ms at the keyframe (#424). **After the update that added the measures (#394), the videos wait for their frames again:** `FRAMES_VERSION` went to 3, so until the first video scan after it finishes, the videos not sampled again yet have no frames, and their `NEAR_DUPLICATE` links (§5, #396) and the frame-based breaks in the `TAKES` chains (#392) are missing. They come back once the scan has sampled every video, and a stopped scan keeps the videos it finished.

**"Scan videos".** A button on the Videos tab (§8) runs the walk and then only the video steps: the metadata (#384), the per-video detectors (`FORWARDED`, #391), the frames (#393), the detectors that read the frames (`BLURRY`, `BAD_EXPOSURE` and `FACES`, #394) and the exact duplicates among videos (#389) today, and later the other video detectors and their group detectors. It purges the expired trash first and forgets the files that are gone, as the normal scan does, since it walks the same way. Only one scan runs at a time. Each tab of Clean has its own scan button, "Scan now" on Photos and "Scan videos" on Videos (§8). The two buttons enqueue the same unique work (`Indexing.WORK`) with KEEP, and "Scan videos" adds a tag of its own (`index-videos`), which the worker reads. So a tap on one button while the other's request waits to start adds nothing, rather than queueing a second scan behind the first. Such a request, like one WorkManager put back after its process was killed or the phone restarted, shows on both tabs in place of the button, as "Video scan · Starting…" or "Photo scan · Starting…" from its tag, with "Stop scanning", which cancels it (#414). The nightly request waits for the night and shows only once it runs. It waits for the lock as "Scan now" does, and the nightly run gives way to it. While a scan runs, its progress and "Stop scanning" show on both tabs in place of the button, and the progress says which scan it is ("Video scan · Phase 2 of 4", "Photo scan · Phase 3 of 5"). "Stop scanning" works on either scan, and a stopped video scan keeps what it finished, as a normal scan does: the metadata is stored in batches of 32, so a stop loses at most the batch it was filling. A video scan the system kills is a request WorkManager runs again, with its tag, and it reads only the videos still without metadata. A video scan walks and records files like a normal scan, so it follows the same rules against a compression batch (§9). The notification names the phase from the video scan's own list, and its header says "Video scan" or "Photo scan" beside the app's name. The last scan's report says which steps it ran, and Settings says "Photo scan", "Video scan" or "Photo and video scan" before its time. The report also keeps when the image steps and the video steps last finished, each carried over by a scan that did not run them, so the time beside "Scan now" is the last scan of the photos and the time beside "Scan videos" the last scan of the videos.

**The night rule.** The night pass analyses videos only after the user has run "Scan videos" once. From then on it takes the new and changed videos after the images, in the same pass. A switch in Settings, "Analyse videos at night", on by default, turns the video part of the night pass off. A second switch, "Analyse images at night", also on by default, turns the image part off (#443). The two are independent: with the images off and the videos on, the night pass walks and runs only the video steps, as "Scan videos" does. With both off, the nightly request stays scheduled and its run only purges the expired trash, with no walk, no model and no notification, and records no scan: the retention promises that the trash empties on its own, and keeping the request avoids scheduling and cancelling it from the switches. Neither switch changes "Scan now" or "Scan videos". "Once" means a "Scan videos" that started (`video_scan_ran` in the settings): a stopped or killed one counts, since the user asked for the videos and the night goes on with what it left. "Scan now" never runs a video step.

**Videos that wait.** The Videos tab shows how many videos wait for a scan ("1,419 videos not analysed yet"): those the index holds out of the trash, without metadata and not marked unreadable (`videosWaiting`). The line goes once none is left. It counts the metadata only: a video whose frames are not embedded yet does not wait by this count. It adds a time estimate once what one video costs on the phone is measured (below).

**After the update.** An update shows no dialog and starts no scan. Letting the head accept videos is the kind of change that must empty `not_images` (above), so the migration from version 6 to 7 adds `media_type`, with `image` on every row, and runs `DELETE FROM not_images`. The lab's schema went from 6 to 7, which refuses an older index file. The migration from 7 to 8 adds the video's own columns (§7), empty, so the first video scan reads every video, and the lab's schema went to 8 (#384). The next normal scan sniffs those files again, records the videos, and "Largest videos" (§6.5, #387) fills. A video category, `EXACT_DUPLICATE` or `FORWARDED` today, says it needs "Scan videos" while it has nothing to list, until `video_scan_ran` is set.

**Phases.** Each scan numbers only its own phases. The normal scan keeps its five (above). A video scan shows its own list, numbered from 1, with the phases it has when it is built: today "Looking for videos", the walk, "Reading the videos", the metadata, "Looking at the frames", the frames, and "Finding copies and takes", the group detectors that accept videos (progress step `video_groups`), so 4 phases. The per-video detectors (`FORWARDED`, #391) run between the metadata and the frames with no phase of their own, since they read nothing from the file. The group detectors come last, so a video group detector can read the frames. The walk's count says "Photos and videos found", since it counts every file it records. A night pass that does both shows the image phases, then the video phases as a second run that says it is the videos: the worker reports which scan a step belongs to (`kind` in the progress, `ScanKind` in the app), and the video steps of the pipeline have names of their own, so the image group detectors are "Phase 5 of 5" and the video metadata after them "Video scan · Phase 2 of 4". The home reloads once the image phases end, as it does at the end of a scan. In a video scan it reloads after the walk and at the end, since neither the metadata nor the frames store a signal.

## 5. Detectors

Each detector looks at an image (or at the image index) and emits **signals**. No detector decides on its own whether an image should be deleted.

| Category | Technique | Notes |
|---|---|---|
| `EXACT_DUPLICATE` | Group by file size, then content hash (xxHash) | Exact, cheap |
| `NEAR_DUPLICATE` | Perceptual hash (pHash/dHash) + embedding similarity | Catches recompressed and resized copies, such as those made by WhatsApp. Suggests keeping the best copy: highest resolution, least compression, original EXIF metadata. For a video: length and frames, which also catch a WhatsApp copy of a camera video (#396). |
| `BURST` | Capture-time clustering + embedding similarity | Suggests the best shot: sharpness, eyes open (face detection). |
| `BLURRY` | Variance of the Laplacian on a downscaled grayscale image | Measure the subject region when one is found, to avoid flagging portraits with an intentionally blurred background. |
| `BAD_EXPOSURE` | Luminance histogram | Pocket shots, black frames, blown-out frames |
| `SCREENSHOT` | Path and file name, image size equal to a screen resolution, no camera EXIF | Nearly deterministic |
| `DOCUMENT` | Text coverage (PP-OCRv4 text detection) + MobileCLIP zero-shot classification | Slides, whiteboards, handwritten notes, homework, receipts, printed pages. Only detection runs: how much text there is matters, not what it says. |
| `FORWARDED` | Messaging-app folder, missing camera EXIF, meme/sticker zero-shot prompts. For a video: the messaging-app folder alone | Forwarded memes and greeting images, and the videos in a chat's folders (#391) |
| `STICKER` | The file is in a messaging app's sticker folder (`WhatsApp Stickers`, `WhatsApp Backup Excluded Stickers`) | Nearly deterministic. On the first phone, 62% of the images were stickers. |
| `TAKES` | Capture time and length of camera videos, broken by frame similarity | Videos only (#392). Takes of one moment, filmed one after the other. No best copy, so the review preselects none. |
| `SHORT_CLIPS` | Length, a camera photo taken beside the clip, the failed take of `TAKES`, dark or blurred frames, no sound and a low resolution in a chat folder | Videos only (#395). Short clips recorded by mistake or beside a photo. A graded score of independent chances, with a threshold of its own for videos (below). |

### Detectors for videos

Eight detectors run on videos so far: `EXACT_DUPLICATE` (#389), `FORWARDED` (#391), `TAKES` (#392, below), `NEAR_DUPLICATE` (#396, below), `BLURRY`, `BAD_EXPOSURE` and `FACES` (#394, below), and `SHORT_CLIPS` (#395, below). Each detector declares the media types it accepts, `mediaTypes` in the app and `media_types` in the lab, images only when it declares none, and the pipeline gives it only those (§7, #383). `check_parity.py` compares the declarations of the lab and the app, detector by detector. The steps that read an image take only images: the metadata read from an image header, the JPEG headers, the perceptual hash, the embeddings and the text coverage. A pipeline test in each side records videos in the index, one of them with metadata that looks like a JPEG's, and checks that no step and no detector receives them. Outside the scan, the Compress page, the steps still missing images in Settings and the Photos tab of the review leave videos out, each with a test. The storage map counts them (#386).

A video signal reuses an image category when it means the same thing: `EXACT_DUPLICATE` (#389), `FORWARDED` (#391), `NEAR_DUPLICATE` (#396), `BLURRY` and `BAD_EXPOSURE` (#394). A new category is only for a new meaning, such as the takes of one moment (#392) or a short clip recorded by mistake (#395). A group never mixes images and videos: `EXACT_DUPLICATE` groups by media type and size before it hashes, and a group detector runs on one media type at a time, the images in the image steps and the videos in the video steps, each with a group run of its own (the videos' is stored as `<detector id>:video`), so a video scan never runs the images' group detectors again, and a normal scan never hashes a video. A video is hashed only when another video has its size, and the hash streams the file in chunks, so a 900 MB video with no twin is never read. The detector's output on images did not change, so its version stays 1. A threshold can differ per media type, so a category that covers both can have one threshold for images and another for videos. The Videos tab lists the categories that have a video detector (§8).

**`FORWARDED` on a video (#391).** Every video in a messaging app's folder is a candidate, its `Sent` folder included (`WhatsApp Video/Sent`, which sits under `.nomedia`, so the gallery never shows it). `ForwardedDetector` takes videos beside images, and a video scores 1, with `messaging_folder` as its evidence. A video outside a messaging folder gets no signal. The detector's version stays 2, since the output on images is the same and no video held a result yet. The decisions:
- *No new category.* The maintainer chose to reuse `FORWARDED`, so the Videos tab lists it beside `EXACT_DUPLICATE` (§8) and the user reads "Forwarded" there too In Italian the name agrees with what it lists, "Inoltrate" of photos and "Inoltrati" of videos (`category_forwarded_videos`), as the maintainer asked.
- *`Animated Gifs` and `Video Notes` are folded in.* Both are folders of a messaging app, so the folder rule already covers them, `WhatsApp Animated Gifs/Sent` included. They did not get the sticker treatment, which gives an image a category of its own and skips the other detectors: the labels hold one video note (deleted) and no animated GIF, so they cannot show that either kind needs one, and a folder rule the sticker folders have for images can be added later.
- *No zero-shot term.* #393 gave videos their frame embeddings, so the class `FORWARDED` leans on exists for them. On the 49 video labels of #390 it did not help: the mean over the five frames of a video's probability for the class (and the maximum, and the class of the mean vector, and one minus the `photo` class) gave an AUC of 0.57 to 0.62 for deleted against kept over all 49, and 0.43 to 0.50 inside the messaging folders, where the chance level is 0.5. The messaging folders held 29 of the 49 videos, 23 deleted and 6 kept. A frame term would also make the signal wait for the frames and need a result forgotten whenever they change, as an image's embedding does, for no gain on the labels. A term can be added to `_video` later, with the frames in the context, without a new category.
- *No resolution and no capture time.* The issue also listed the resolution and the camera metadata. Every video of the labels in a messaging folder has no MP4 creation time and every camera video has one, so the capture time says what the folder already says, and the resolutions of the kept and deleted chat videos overlap (352×640 to 848×480 in both). Neither is in the formula, and a video's metadata does not read camera make or model, which an image's EXIF has.
- *A score of 1, and `Sent` not above the rest.* The issue asked for a stronger signal in `Sent`, and the first version scored a received video 0.6 and a sent one 0.8. Two things undid it. The labels do not back it: 15 of the 20 videos in `Sent` were deleted and 8 of the 9 received ones. And `FORWARDED` has one threshold, which the photos' slider sets (§8): raised past 0.6 to see fewer forwarded photos, it would have dropped every received video from the Videos tab without a word. At 1 no position of the slider hides a video, which keeps recall over precision (D4), so the video section of the thresholds screen still waits for a graded video score (#394). The maintainer chose this on 2026-11-17. The order among these videos goes by their size (§6.6, #397).
- *On the labels.* The signal makes 30 of the 50 videos in the lab's index candidates and catches 23 of the 35 deletes (66%) with 6 of the 14 keeps flagged. The 12 deletes it misses are all in the camera folder, for the detectors still to come (#392, #394, #396). Nothing here is tuned: the folder is the whole rule.
- *Where it runs.* In the video steps only, after the metadata and before the frames and the group detectors (`_video_detectors` in the lab, `analyzeVideos` in the app). It reads no frame, so it does not wait behind the longest step, and a "Scan videos" stopped while the frames are read already has its signals. A video whose header did not read is left out, as an unreadable image is. The step reads nothing from the file, so it has no progress step or phase of its own.

**The takes of one moment (#392).** The user films one thing several times and keeps every take: on the maintainer's phone, 95 camera videos (28.3 GB) start within five minutes of the end of another one (#172). `TAKES` is a group detector that accepts videos only. It takes the videos in a camera folder (`DCIM`) with a capture time, in the order of `captured_instant`, and a video joins the takes of the one before it when it starts at most `TAKES_MAX_GAP_MS` (5 minutes) after that one ends, its start plus its length. The takes compare one clip with another, so they use the instant and not the local wall clock of `captured_at`, which goes back an hour at the autumn clock change and depends on the zone each clip was read in (§7). A video with no length ends where it starts. A sent or saved copy is no take, whatever its time: it is a copy, which #396 will find. A screen recording is no take either: a Galaxy saves them to `DCIM/Screen recordings`, and that folder is left out. When both videos have frames (#393), the chain also breaks where the two look nothing alike: the closest pair of their frames, by the cosine of their embeddings, is below `TAKES_MIN_COSINE` (0.5). Without the frames of both, time alone decides, as for `BURST`. A video in a group of takes gets a `TAKES` signal of score 1, with the group, its role and the number of takes in its evidence. A take at most `SHORT_TAKE_RATIO` (half) as long as the next take of the same moment gets the role `short_take`, which reads as a failed start that #395 can use. Every other take is `take`. Unlike `BURST`, the chain does not drop a single different video between two alike ones: five minutes is long enough for the moment itself to change.

**A kept take stays kept (#431).** The group id comes from the first take's path, and the roles from the next take's length, so trashing the failed start of a moment, the case the role exists for, gives the takes left a new group id and can change their roles. A take's signal identity (§6.3) is therefore its category alone, with no group and no role, in the lab and in the app: a take the user kept never comes back as a take, even when its group or role changes. The cost is that a take kept in one group is not offered again when a new take joins it later. The new take is offered, and its page shows the kept ones beside it.

- *A new category, not `BURST` for videos.* `BURST` means shots seconds apart with the sharpest kept, and its whole page assumes a best copy. Takes are minutes apart, compared by length and frames rather than sharpness, and have no best copy (next point). The rule of this section already kept a new category for a new meaning. A category of its own also gets its own row and name on the Videos tab ("Takes of one moment"), and the Photos tab leaves out a category whose detectors take only videos (`VIDEO_ONLY_CATEGORIES`).
- *No best copy, and nothing preselected.* The review's group pages keep a best copy and preselect the others for the trash (§8). Which take to keep is not obvious: the longest, the sharpest and the last each fit some moments. So the first version picks none. Every take is a candidate at score 1 (recall first), with the role `take` or `short_take` and never `best`, and the page shows the takes side by side with their length and size and preselects nothing. The score is fixed, so `TAKES` has no threshold slider (§8). A later version can add a best take once the labels show which one the user keeps.
- *Tuning.* The labeled videos of #390 (49 keep or delete, 20 of them camera videos with a capture time) hold no two camera videos within 13 minutes of each other, so they cannot tune the gap. Five minutes comes from the phone's measurement in #172 (95 videos in 34 groups, against 53 in 18 at one minute), and recall first takes the wider one, since the frames break a chain that time alone would join. For the frames, the closest thing in the sample to two takes of a moment is the first two and the last two frames of one camera clip: their closest pair was at least 0.59 for all 20 camera clips, while 152 of the 190 pairs of different camera clips were below 0.5. So 0.5 keeps every such pair together and still splits most unrelated ones.

**Near duplicate videos and sent copies (#396).** WhatsApp re-encodes a video it sends, so the copy in `Sent` (684 files and 5.2 GB on the maintainer's phone, #172) never matches its camera original by content hash, and neither does a video received twice in two qualities. `NEAR_DUPLICATE` takes videos as well as images, in the same detector with a rule of its own for videos. Two videos are linked when their lengths are at most `VIDEO_MAX_DURATION_GAP_MS` (100 ms) apart, they are not two takes (below), and their frames (#393) look alike: each frame of either video is matched with the closest frame of the other by the cosine of their embeddings, and the mean of those cosines over the frames of both must reach `VIDEO_MIN_FRAME_COSINE` (0.80). The videos are sorted by length and each is compared only with the ones up to the gap longer, so the length cuts down the pairs. Linked videos form a group, as images do. The best copy is the one in the camera folder (`DCIM`), then one outside a messaging folder, then the highest resolution, then the highest bitrate. It gets the role `best` and score 0, and every other copy `inferior` and score 1. The output on images did not change, so the version stays 3. The decisions:
- *The count first.* The issue asked whether enough `Sent` videos still have their original on the phone. The lab's sample has 21 of the phone's 684 `Sent` videos and 20 of its 236 camera videos, drawn apart for each folder (#390). One `Sent` video has its camera original in the sample, and two more are one video sent twice in two qualities. Since the sample holds about 8.5% of the camera videos, even a phone where every sent video had its original would show about 2 such pairs. One rules out "almost none" and says little more, so the detector was built, and a count on the whole phone is left to the first scan with it.
- *`NEAR_DUPLICATE`, not a category of its own.* A WhatsApp copy of a video is what a WhatsApp copy of a photo is, a recompressed copy with a best one to keep, which the rule of this section gives an existing category (`EXACT_DUPLICATE` and `FORWARDED` did the same). So the Videos tab has a "Similar copies" row, with the same name in both languages.
- *Length and frames, not the image rule.* A video has no perceptual hash, and one embedding would be the mean of its frames, which loses where they are in the clip. The frames are matched by their closest frame and not by their time: an HDR video's frames are keyframes (§5), fewer than five on a short clip and up to half a second off the times of its SDR copy's exact frames.
- *No link without frames or a length.* A length alone is no evidence, since many clips share one, so a video with no stored frames or no duration is linked to none. `TAKES` lets time alone decide without frames, but its time is a capture instant in a camera folder, which says far more than a length. A copy that WhatsApp trimmed before sending has another length, and this rule misses it.
- *The best copy by folder first.* The issue asked for the camera folder first, then resolution and bitrate. A camera original has the higher resolution anyway, so the order matters only when a larger copy sits elsewhere, and the original is the one to keep then too. For images the folder is the last tie-break, after resolution, compression and EXIF, which a video has no equivalent of.
- *The group id is the best copy's path.* #392's review found that a group id taken from a take the user trashes changes the group of the takes left, so a kept take came back (§6.3). Here the id comes from the copy the review keeps, so trashing a copy leaves the others in the same group with the same role, and a kept copy stays kept. If the best copy itself is trashed or moved later, the next copy becomes the best and the group id changes, so the copies the user kept come back once, as images do (§6.3). That is the rule for every group with a best copy, not the takes' bug. The identity of the signal stays category, group and role: a better copy that turns up later makes the kept one `inferior` in a new group, a new signal by §6.3, which is what it should be.
- *A copy scores 1.* The issue asked for the strongest score for a sent copy whose original is on the phone. `NEAR_DUPLICATE` has one threshold, which the photos' slider sets, so a graded score would let the slider hide videos without a word, as for `FORWARDED` (§5). A copy scores 1, the same as `FORWARDED` gives every video in `Sent`, so a sent copy with its original does not come before one without in the review's order: both score 1, and their size orders them (§6.6). What it gains is its group page, which shows the original beside it and marks the copy for the trash. A sent copy whose original is gone keeps only `FORWARDED`.
- *Takes are not copies.* Two videos in a camera folder that both have a capture instant, and whose instants differ, are never linked, whatever their length and frames: they were filmed apart, so they are takes of a moment, which `TAKES` lists with nothing marked. A copy saved to the camera folder, such as a re-export from the gallery's editor, keeps its original's instant or has none, so it still links. Without this rule, two takes of about one length and alike frames would have formed a `NEAR_DUPLICATE` group whose page marks one take for the trash.
- *Tuning.* Both pairs of the sample had lengths equal to the millisecond, and their frames scored 0.887 (a 4K HLG original against its copy, keyframes against exact frames) and 0.980 (one video sent at two qualities). Of the other pairs of the 50 videos, the closest within 100 ms of one length scored 0.596, and within 500 ms 0.757. 0.80 sits between the two groups. Both are starting points from two pairs, and the length gap does most of the work: with the length left out, 11 of the 1,225 pairs reach 0.80, and 9 of them are not copies, 0.7% of the unrelated pairs. A phone with about 1,000 videos has around 10,000 pairs within 250 ms of one length, and at that rate about 70 of them would reach 0.80, each a false link that marks an unrelated video for the trash. So the gap is 100 ms: a re-encode moves a length by an audio frame or two (about 21 ms each for AAC at 48 kHz), and both copies in the sample were 0 ms apart. Three of the four videos it groups in the sample are in `Sent`, candidates under `FORWARDED` already, and the fourth is a best copy, so it makes no new candidate. On the labels, the maintainer kept the sent copy whose original is on the phone, and deleted both copies of the video sent twice.

**`BLURRY`, `BAD_EXPOSURE` and `FACES` on a video (#394).** The three detectors of an image take videos too, and read the frames of #393. A video of one second of black, or out of focus from start to end, is deletable whatever its length, and a video of people is more likely a memory. The decisions, each made on the 49 video labels of #390 (35 deleted, 14 kept; 12 of the deletes and 8 of the keeps are camera videos, the rest are in messaging folders):

- *Measures, not frames.* The frames are never stored (§4), so the frames step measures each one while it decodes it, with the code the detectors have for an image (`frame_measures.py`, `FrameMeasures.kt`): the Laplacian variance of its sharpest region (`BLURRY`), four luminance percentiles (`BAD_EXPOSURE`) and its faces (`FACES`, YuNet on the letterbox of the frame). The five rows of a video go in `frame_measures` (§7), in the same transaction as the vectors. The detectors turn them into one signal each, so a rule or a threshold can change with no video decoded again. `FRAMES_VERSION` went to 3: the videos sampled before it have no measures, so the first video scan with the model samples every video once more. What the measures add to the 1.3 s a video costs on the phone (#393) is not measured yet: the grayscale of a 4K frame and YuNet on its letterbox come on top of the decode and the model, and `VideoFramesDeviceTest` should time them before the maintainer's videos are scanned again. The lab's `--no-embeddings` skips the frames step, so it gives a video none of these three signals.
- *Where they run.* After the frames step and before the group detectors, from the measures it stored (`_video_detectors` with `uses_frames` in the lab, `analyzeVideos` with `usesFrames` in the app): they go after the step they read, and they need no decode. A detector that reads frames declares `uses_frames`, as one that reads an embedding declares `uses_embeddings`, so a new sampling of the frames forgets its stored results, and a video with no measures yet is left alone and gets no empty result stored. A scan stopped in the frames step keeps the measures of the videos it finished, and their signals come at the next video scan.
- *The video's score is the median over its frames.* "A video gets the signal when most of its frames do" asked for the mean, the median or the share of frames over a threshold. The median makes a video blurry or dark when most of its frames are, so one frame out of focus, or a hand over the lens, does not flag it, and the score stays graded, so it has a threshold and a slider (§8), where a share needs a second number. For an even number of frames it is the mean of the middle two, as an HDR video with four keyframes has. `BLURRY` scores the median frame's sharpest-region variance as an image does (half score at 100), and `BAD_EXPOSURE` takes the median of each of its three cases over the frames and the strongest one names the video ("dark" says most of the frames are). On the labels, at the same threshold of 0.15, the median flags 13 deletes and no keep, the mean 16 and no keep, the lowest frame 5 and no keep. The mean catches three videos more, but also catches a video with one frame out of focus, which is what the issue asked not to flag. Motion blur is normal in a video frame, which is why the threshold below is lower than the photos'.
- *Thresholds of their own.* The photos' threshold for `BLURRY` is 0.4, which flags 2 of the 35 deleted videos. A video threshold of 0.15 flags 13 and no kept video (at 0.10, 18 deletes and 2 keeps; at 0.05, 28 and 10), with the nearest kept video at 0.12. `BAD_EXPOSURE` flags 4 deletes and no keep at any threshold from 0.05 to 0.45, so it keeps the photos' 0.4. Both sit in `VIDEO_THRESHOLDS` (`ranker.py`, `Ranker.kt`), which `check_parity.py` compares. The 14 keeps are few, so the margin of 0.03 over the nearest is not a promise, and recall comes first (D4): a kept video the threshold lists costs a glance. A video is held to `VIDEO_THRESHOLDS` where its category is in it, so the photos' slider can never hide a video (§6.1, §8).
- *On the labels.* With `FORWARDED`, the three catch 27 of the 35 deletes (77%, from 66% with `FORWARDED` alone), with the same 6 keeps flagged: none of the kept videos is made a candidate by the new detectors. `BLURRY` alone flags 13 deletes (2 that nothing else flags) and `BAD_EXPOSURE` 4 (1). Of the 12 deletes in the camera folder, which `FORWARDED` could not see, they catch 4. The other 8 have nothing these detectors read, and are left to #395 and #396.
- *`FACES` lowers the video and never removes it.* The signal is the mean over the frames of each frame's most confident face, 0 for a frame with none, with the weight of an image's (0.5, §6.2). A person in two frames of five protects a video a little, in all five a lot, and the median would have been 0 for most videos with people, since a face is often in some of the frames only (AUC of deleted against kept 0.52 for the median, 0.59 for the highest frame, 0.62 for the mean and 0.63 for the share of frames with a face). Faces show in at least one frame of 23 videos: 9 of the 14 kept (64%) and 14 of the 35 deleted (40%). With the signal, the chance that a labeled delete comes before a labeled keep in the review order is 0.66, without it 0.57.
- *`DOCUMENT` and `SCREENSHOT` on frames: no.* They would find a filmed slide or a screen recording, and the maintainer's phone has no screen recording. On the frame vectors of the 49 labels the zero-shot class of `DOCUMENT` gave an AUC of 0.45 to 0.46 for deleted against kept and reached 0.5 on 2 videos, and that of `SCREENSHOT` 0.47 to 0.50 and reached it on none. The size rule of `SCREENSHOT` would flag 23 of the 50 videos, since a phone's own videos have its screen's size. A video detector for either can come when a library has the videos to show it.

**Short clips (#395).** A short clip frees little, but the maintainer wants them found to keep the phone tidy: on their phone 68 camera videos of 3 to 10 seconds hold 4.7 GB, and the 153 WhatsApp clips under 10 seconds that MediaStore lists hold 0.3 GB. A 4 second clip of a person can be a memory all the same, so length is evidence and not a verdict. `SHORT_CLIPS` is a group detector that accepts videos only, in the last video step with the other group detectors (§7), and it gives each video shorter than `SHORT_CLIP_MAX_MS` (15 s) one signal whose score combines these pieces, each a chance with its own weight:
- *Length*, `DURATION_WEIGHT` (0.4) up to `FULL_DURATION_MS` (5 s), fading to 0 at 15 s. A very short clip is the same measure and not another piece.
- *A photo beside it*: a camera photo (a file in `DCIM`, but not its `Screenshots` folder, where a Samsung saves screenshots) with a capture time at most `PHOTO_WINDOW_MS` (a minute) from the clip's, either side, whose embedding is at least `PHOTO_MIN_COSINE` (0.6) alike a frame of the clip. `captured_at` of both is a local wall clock, which is what §7 kept it for. Without the photo's embedding or the clip's frames, time alone decides, as for `TAKES`. Weight `PHOTO_WEIGHT` (0.5).
- *A failed take*: the video has the role `short_take` in the chain `TAKES` builds (§5, #392). The detector calls `TakesDetector` on the same videos and reads its roles, so the chain, its gap and its frame break are not written twice. Weight `TAKE_WEIGHT` (0.6).
- *Recorded by mistake*: the video is dark, bright, flat or blurred on most frames. It is the larger of the video's own `BAD_EXPOSURE` and `BLURRY` scores, which are the median over the frames (#394), counted when at least `MISTAKE_MIN_SCORE` (0.15, the `BLURRY` threshold for videos) and weighed by `MISTAKE_WEIGHT` (0.8) times that score.
- *A GIF-style clip*: no audio track, a short side of at most `GIF_MAX_SIDE` (480) and a messaging app's folder. Weight `GIF_WEIGHT` (0.6).

The score is one minus the product of what each chance misses, as in `SCREENSHOT`. Faces and favourites are not read: they lower the video in the ranker as for any video, and drop no one (§6.2). The evidence holds the length, what each piece added (`duration_chance`, `photo_chance`, `failed_take_chance`, `mistake_chance`, `gif_chance`) and the kind of mistake, and the review's reason line names the piece that added the most. The decisions, each taken on the 49 video labels of #390 (35 deleted, 14 kept) unless it says it could not be:
- *Do the pieces combine as independent chances? Yes: the five pieces are chances of one noisy OR, and length is the first.* A video shorter than 15 s gets the length term, so the other pieces come on top of it. Of the 26 labeled videos flagged at the default threshold, another piece fired on 14 (a dark or blurred video on 12, a photo beside it on 3, one both) and all 14 were deleted, against 9 of the 12 with length alone. The 6 labeled keeps under the length term had no other piece: they were not dark, not blurred past 0.10 and not beside a photo. The sample is too small to show that the pieces are independent, and it does not show that they are not. What decides it is the same as for `SCREENSHOT` and `FORWARDED`: each piece reads something else (the clock, the pixels, the folder, the neighbours), so a clip that is short and dark is more likely deletable than one that is only short, and a noisy OR raises the score for each reason, where taking the largest would not. The one pair of pieces that read one measure, a very short clip and a short one, is not two pieces.
- *Length gates the pieces.* Without a limit a photo beside a 10 minute video would flag it. The labeled videos up to 10 s were deleted 23 times of 26, those from 10 s to 30 s 7 times of 16, below the base rate of the labels (35 of 49), so past 15 s a video gets no signal, whatever else it has. A video with no length gets none either, since nothing says it is short. The 17.5 s clip beside a photo that the maintainer kept is left out by this rule.
- *Weights and the default threshold of 0.3.* The weights are starting points chosen to give a clip its length and an extra chance each: a clip up to 5 s scores 0.4 alone, so the default lists it with no other evidence, and one of 7.5 s scores 0.3. Over the labels the threshold flags 23 of the 35 deletes and 3 of the 14 keeps (at 0.2, 25 and 3; at 0.35, 20 and 1; at 0.4, 17 and 1). The step from 0.3 to 0.35 drops the two kept clips of 6.5 s (0.34) and 3 deletes, with a margin of 0.01 on a delete at 0.33, so the value is a starting point from 49 videos and recall comes first (D4). Length alone at 0.3 flags 17 deletes and 3 keeps, and the other pieces add 6 deletes and no keep.
- *A photo beside, on 20 camera videos.* 4 of the 20 camera videos of the labels have a camera photo within a minute in the lab's index, 3 deleted (cosines 0.73, 0.91, 0.93) and the 17.5 s one kept (0.89). The index holds 431 photos of the camera folder, a sample of the phone's, so the real count is higher. For two unrelated photos and clips the cosine of the closest frame is below 0.6 for 98.8% of the 21,350 pairs of the sample (0.62 at the 99th percentile), so 0.6 lets almost no unrelated pair through, and a clip taken beside a photo of another scene is not counted.
- *Failed takes and GIF-style clips could not be measured.* The labels hold no two camera videos within 13 minutes, so `TAKES` finds no chain in them and no clip has the role `short_take` (the same limit as the gap, §5), and all 50 videos in the index have an audio track, so no clip reads as a GIF. Their weights are a guess: both are as strong as a photo beside the clip, since a failed take has a longer take to prove it and a silent clip in a chat folder is nearly always a converted GIF. The first scan on the maintainer's phone is where they get measured, and the `GIF_MAX_SIDE` of 480 is the short side of the labeled chat videos (320 to 480 for most of the clips under 10 s), not of an animated GIF.
- *Recorded by mistake takes the video's own signals.* The median frame of `BAD_EXPOSURE` and `BLURRY` already says what most frames look like (§5, #394), so the piece takes their scores and adds no measure to the frames step. The floor of 0.15 keeps the usual motion blur of a camera clip (a median score of about 0.1) from adding a chance to every clip. 12 of the flagged deletes get this piece and no keep does: 3 are dark and 9 blurred.
- *On the labels, with the other detectors.* `FORWARDED`, `BLURRY` and `BAD_EXPOSURE` flag 27 of the 35 deletes and 6 of the 14 keeps. With `SHORT_CLIPS` at 0.3 they flag 31 of the 35 deletes (89%, from 77%) and 7 of the 14 keeps. The new detector alone adds 4 deletes and 1 keep, and takes the camera videos from 4 to 8 of the 12 deleted ones, with 1 of the 8 kept.
- *The order of the list.* A video's score is multiplied by its size (§6.6), and a short clip is 0.3 MB to 640 MB at a score of 0.3 to 0.95, so the order of "Short clips" is the order by size. On the flagged labels the first 5 reviews find 0.48 GB of the 0.57 GB of deletes and 1 keep, against 0.32 GB and no keep by score alone. The linear factor stays, as the first step of §6.6 decided, and the order by score is a choice left to the maintainer.
- *Where it runs, and what stales it.* In the video group step, after the frames and the detectors that read them, with the measures of the frames of #394 and the photos of the index. Its own input key (§7) carries the versions of `TAKES`, `BLURRY` and `BAD_EXPOSURE`, so a new version of any of them runs it again with no other bump, and the counts of the measures and camera photos.
- *The trash and the photo beside a clip.* The camera photos in the trash count too, since the index keeps their rows: a trashed photo beside a clip still says the clip was meant to be one. When the trash is emptied or a photo expires, the row goes at the next scan, the count of the key changes, and the clip loses that chance. A clip that was listed only because of the photo can then leave the list, or fall below the threshold.

### Order and stickers

The detectors that read no embedding run first (`BLURRY`, `BAD_EXPOSURE`, `SCREENSHOT`, `FACES`, `STICKER`), with the perceptual hash, and on a sticker only `SCREENSHOT` and `STICKER` (below). Then the embeddings are computed, and `DOCUMENT` and `FORWARDED`, which read them, run on each batch as soon as its embeddings are stored (§7), and last the group detectors. On the first phone's index (11,308 images) the sticker folders held 6,056 of them, and `STICKER` and `SCREENSHOT` made 6,847 of the 8,132 candidates, so most candidates are there before the first embedding.

**Real images go before stickers.** The metadata step and the detectors that read no embedding take the real images first and the stickers after them, in both the lab and the app, so the candidates a user is looking for reach the home screen before the thousands of stickers. Only the order inside these two steps changes. Every sticker still goes through both (the second with only the detectors it runs, below), no result depends on the order, and the group detectors still get the images in index order. Stickers stay in the same steps instead of a phase of their own, which would change the phases the scan screen names. The metadata step reads several files at once but stores them in this order, so a sticker's metadata is never stored before a real image's. Two limits of the detectors step. Workers overlap at the switch, so the last real images and the first stickers run at once. An image that ran out of memory runs again after the queue is empty (§7), so a real image can come back after the stickers. The time left of the phase (§4) follows the images of the last 30 seconds, so it reads the real images' cost while the stickers are still ahead, and moves when they start.

**A sticker runs only the perceptual hash, `SCREENSHOT` and `STICKER`.** An image in a messaging app's sticker folder is not embedded, and `DOCUMENT`, `FORWARDED`, `FACES` (YuNet), `BLURRY` and `BAD_EXPOSURE` do not run on it. It would only have been listed under `STICKER` anyway (§8), so skipping them changes which other categories a sticker appears under, which the review already hides, not whether it is a candidate (D4). The skip is in the list of detectors each sticker runs, not only in dropping their results afterwards, which would still run them on every sticker at every scan. `BLURRY` and `BAD_EXPOSURE` cannot raise a sticker's likelihood, since its `STICKER` signal already gives the highest an image can have, and the full size view no longer shows "Blurry" or "Too dark" under "Sticker" (522 stickers on the first phone's index, #359). `FACES` only reorders the `STICKER` list, and was not shown to help there (§6.2). `BURST` ranks its shots by blur's stored measure, and decodes a shot again (`peakVariance`) when blur stored none, so a sticker in a burst would be grouped and ranked the same, only more slowly. No sticker on the first phone's index is in a burst anyway. None of the three gets a new version, since each gives the same output for the same image. On the first phone, #343 estimated the skip at about 60 to 100 s of a first scan for `FACES` and 40 to 80 s for blur and exposure, half of that after the shared decode (§7). `STICKER` is still 1 for every sticker, so it keeps its place in the review order. The pipeline recognises a sticker with `isStickerFolder`, the rule the `STICKER` detector uses, so the two cannot disagree. This takes 6,056 of the 11,308 images off the embedding phase, 54%. A sticker embedding from an earlier scan stays in the index, but the pipeline does not read it, and the `DOCUMENT`, `FORWARDED`, `FACES`, `BLURRY` and `BAD_EXPOSURE` results an earlier scan stored for a sticker are dropped at the next scan, in both the lab and the app, so a library gives the same result, reasons included, whether or not it was scanned before this rule.

**Groups still see stickers, by perceptual hash only.** `NEAR_DUPLICATE` links two images when their hashes are close or their embeddings are close, and `BURST` uses embeddings only to break a time chain, and only when both shots have one (§7, #108). A sticker with no embedding is linked by hash alone. No sticker on the index has a capture time, so none is in a burst, with or without an embedding. Both detectors already handle an image without an embedding, so neither changes and neither gets a new version. The cost is the groups that only an embedding made. On the same index 1,395 stickers are in a near-duplicate group when embeddings are used, 874 of them by hash too, so 521 leave their group entirely. They stay candidates under `STICKER`. A non-sticker whose only link was an embedding link to a sticker leaves its group as well: 2 did, both best copies of their group, and no candidate was lost. Embedding links are not kept for stickers because that is the 54% the phase would spend. The group fingerprint counts the embeddings, so it changes once on a phone that scanned before this rule and the groups are computed again. It also counts the stored perceptual hashes, so an image whose hash failed on one scan and works on the next is grouped again without waiting for another image to change. A content hash works another way, since the exact-duplicate detector computes it while it runs and only for files that share a size. The detector skips an image whose hash fails, and the run stores the paths that failed with its fingerprint. The next scan hashes those files again before it compares fingerprints: if one now reads, the detector runs, and if all still fail, it skips. So a file that can never be read does not make the detector run on every scan, and one that becomes readable is grouped at the next scan.

### MobileCLIP

[MobileCLIP](https://github.com/apple/ml-mobileclip) is a compact image–text embedding model that runs on phones. A single embedding per image, computed once and cached, serves three purposes:

- near-duplicate search (cosine similarity between embeddings);
- zero-shot classification against text prompts such as *"a photo of a projector slide"* or *"handwritten homework on paper"*;
- natural-language search later on.

With about 10,000 images, the embeddings take roughly 20 MB (512 float32 values per image), and comparing every pair directly is feasible without an approximate-nearest-neighbor index.

**Variant: MobileCLIP2-S0, as ONNX.** [MobileCLIP2](https://arxiv.org/abs/2508.20691) (2025) keeps MobileCLIP's architectures and improves their training: S0 goes from about 68% to 71.5% ImageNet zero-shot accuracy at the same size. S0 is the smallest variant (a 45 MB float32 image encoder), and its ONNX export ([plhery/mobileclip2-onnx](https://huggingface.co/plhery/mobileclip2-onnx), `onnx/s0/`, pinned to a revision) runs unchanged in the lab and in the app, on ONNX Runtime in both. Both compute the same embeddings, so golden fixtures can compare them directly. The export was checked against Apple's open_clip weights on the golden fixtures: image and text embeddings agree to within 1e-6. Input: shortest side resized to 256 px (bilinear), center crop to 256×256, RGB scaled to [0, 1], no normalization. Zero-shot uses the checkpoint's learned temperature, 64.33. The text encoder (254 MB) only turns prompts into embeddings. The lab computes those once into `lab/src/cribrum_lab/prompt_embeddings.json`, and the app build copies that file into its resources, so the text encoder never goes on the phone.

On the first phone's 912 labels, MobileCLIP2-S0 raised recall from 73% to 81% at the starting thresholds. With thresholds suggested for 80% recall, it flags 117 kept images instead of 146, for about the same number of candidates. Its similarities spread like MobileCLIP-S0's: at 0.90 it links 3,125 pairs of the 10,000 images against 2,905, so the NEAR_DUPLICATE and BURST thresholds stayed.

**License.** The MobileCLIP2 weights come under Apple's Machine Learning Research Model license, which allows research and other non-commercial use only. Cribrum is a personal, non-commercial app, so this is accepted. A commercial release would need another model, such as MobileCLIP-S0 (Apple sample code license) or Meta's Perception Encoder (Apache 2.0). The PP-OCRv4 text detector is Apache 2.0, which asks for the license text next to a redistributed copy. The pinned RapidOCR revision ships none, so the app does not package a notice yet: add PaddleOCR's license to the APK before any release.

On the dev machine (Ryzen 5 3600XT, CPU only), decoding and preprocessing take about 80 ms per image on one core (12 worker processes share it), and inference about 19 ms per image in batches of 16 on all cores: roughly 5 minutes for 10,000 images. These numbers were measured with MobileCLIP-S0, which has the same image encoder architecture (MCi0).

**Video frames (#393).** A video becomes five frames to MobileCLIP, and later to the detectors that read pixels (#394). The rule and its reasons:

- *Which times.* The middle of each of five equal slices of the video, half a second off each end, where a clip fades in, starts black or catches the hand on the button. A clip under two seconds keeps a quarter of itself off each end instead, a clip too short for five distinct milliseconds gets fewer frames, and one with no duration its first frame (`frameTimes` in `Frames.kt`, `frame_times` in `frames.py`). Five is the issue's starting value: the lab picks the number once the video labels of #390 exist. `FRAMES` and `MARGIN_MS` are compared by `check_parity.py`.
- *The exact frame for SDR, the nearest keyframe for HDR.* An SDR video's time gets the frame whose timestamp is closest to it: `OPTION_CLOSEST` on the phone, and in the lab a seek to the keyframe before it and a decode up to it, a tie going to the earlier frame. A keyframe alone is faster, one decode a frame, but it sits up to a group of pictures before the time. A camera clip has a keyframe about every second, but a re-encoded clip or a screen recording can have one for many seconds, and then several of the five fall on the same frame, often the first, which is the start the margin keeps out. #396 also compares a camera original with its WhatsApp copy frame by frame, and the copy has keyframes of its own, so keyframes of the two land at other moments where exact frames land at the same ones. The price is decoding from the keyframe up to the time: 100 to 530 ms a frame on the maintainer's phone (§4). An HDR video (`hdr` in the metadata, PQ or HLG) takes the keyframe nearest each time instead: on the maintainer's phone (Galaxy Z Fold7, Android 17), `OPTION_CLOSEST` returned no frame for any HDR video tried, the HLG and PQ fixtures and three of the phone's own 4K 60 fps HLG clips, after about 1.1 s each (the decoder reports `WOULD_BLOCK`), and so did `getScaledFrameAtTime` and `getFrameAtIndex`, while `OPTION_CLOSEST_SYNC` gave a frame every time. 158 of the phone's 240 camera videos are HLG, so exact frames would have left most of them without frames. The maintainer decided on 2026-11-16 to take keyframes for HDR and keep exact frames for SDR. AOSP's MP4 extractor seeks for `OPTION_CLOSEST_SYNC` in two steps: to the frame nearest the time, then to the keyframe nearest that frame, a tie going to the later one each time (`findSampleAtTime` and `findSyncSampleNear` in `SampleTable.cpp`). The lab copies both steps from the frame and keyframe times it reads from the demuxer, without decoding, up to the second keyframe past the last time. A WebM or Matroska HDR file goes through `MatroskaExtractor` instead, which seeks by its cues, and was not checked. On the maintainer's 4K HLG clip (below) the phone took 1449 ms to the keyframe at 1012, 3347 to 2911, 5245 to 4810, 7143 to 6709 and 9041 to 8609, the lab's choice for each. Times that land on one keyframe give it once, stored under the first of them, so an HDR video can have fewer than five frames, as a very short clip already could. The retriever does not say which keyframe it took, so the phone asks `MediaExtractor` first: `seekTo` with `SEEK_TO_CLOSEST_SYNC`, which goes through the same extractor code, and `sampleTime` give each keyframe's time without decoding, and the retriever is then asked for the frame at that time. So both sides tell keyframes apart by time, and a static or dark clip, whose keyframes can look the same, keeps the same frames on both. In the lab only keyframes leave the decoder (`skip_frame` `NONKEY`): FFmpeg's MP4 seek works on decode times, so a seek to a keyframe's time often lands on the keyframe before it, and without the flag the lab decoded a whole group of pictures to get back, 19.5 s for the five frames of the maintainer's clip against 4.7 s with it, with the same pixels. These are the limits above, for HDR only, and `FRAMES_VERSION` went to 2.
- *One vector a frame, not their mean.* The index keeps each frame's vector by its time (`frame_embeddings`, §7). #396 compares two videos frame by frame and #395 a photo with the frame closest to it, which a mean cannot give back, while a detector that wants the mean (#171) takes it in one line. It costs 10 KB a video, 14 MB for the 1,419 videos of the maintainer's phone.
- *The same preprocessing as an image.* A frame goes through MobileCLIP's steps from its full size, upright (`modelInput` in `MobileClip.kt`, `model_input` in `mobileclip.py`), as an image with no draft mode does. A 4K frame is 33 MB as a bitmap on the phone, dropped as soon as its pixels are copied, so memory holds one frame at a time.
- *HDR, tone mapped as the phone does (#424).* The phone takes the frame `MediaMetadataRetriever` gives, which the platform has tone mapped to SDR in its own way, which the app cannot pick, and the lab copies what the maintainer's phone does to its own camera's clips. The lab first tone mapped with FFmpeg's swscale, which maps HDR reference white (203 cd/m², 75% of the HLG signal, ITU-R BT.2408) to SDR white and clips above it. On a 4K 60 fps HLG HEVC clip of the phone (Galaxy Z Fold7, Android 17), compared at the same keyframes, that was about 1.85 times brighter than the phone (210/212/214 against 112/113/114 mean RGB on one frame), clipped up to 47% of a frame where the phone clipped none, and reached a cosine of 0.957 to 0.988. The phone's frames fit a plain curve instead: HLG's inverse OETF (BT.2100) for scene light from 0 to 1, no OOTF, times 0.9 (`HDR_GAIN`), BT.2020 to BT.709 primaries, clipped and sRGB encoded (`_tone_mapped` in `frames.py`, in numpy, with lookup tables and in bands of 256 rows: about 0.5 s and 40 MB a 4K frame, where all rows at once took 280 MB). On the clip's five keyframes that gives a cosine of 0.9993 to 0.9999 with the phone's embedding, a mean colour within 3.3 levels on every channel (112.6/113.6/114.6 against 112.0/113.0/114.0, and 54.9/57.4/60.3 against 52.0/54.3/57.0 at the worst), and no clipped pixel on either side. The candidates tried and dropped, on the same five frames: swscale to sRGB, gamma 2.2 or BT.709 (cosine 0.956 to 0.988, 45 to 107 levels too bright), the signal shown as SDR with no tone mapping (0.962 to 0.989, 40 to 60 levels too bright), the same with BT.709 primaries only (0.975 to 0.990), and the curve above with the BT.2100 OOTF for 1000 cd/m² (gamma 1.2) or a gamma 2.2 output (at their best gain, a worst cosine of 0.997 and 0.998, and up to 6 levels off). PyAV's FFmpeg has no `zscale`, and its `tonemap` filter needs linear light that only swscale could give, so no FFmpeg filter chain was tried beyond swscale. PQ takes the same curve with PQ's EOTF in cd/m² over HLG's nominal peak of 1000: no PQ clip of the phone was measured, so this half is a guess. The 64×48 HLG and PQ fixtures do not follow the curve on the phone: it gives back about their raw signal, 126/124/123 mean RGB for HLG and 126/125/124 for PQ, close to the SDR source `clip.mp4` (126/125/124). The lab's curve gives 102/112/108 and 109/121/117 there, its old swscale mapping 145/157/147 and 130/140/130, and the raw signal read as SDR 126/124/122 and 126/125/123 (cosine 0.989 and 0.994 with the SDR source's frame). So the phone tone maps its camera's 4K clips and not these small files, most likely because they take another decoder, and no one curve matches both. The lab follows the camera clips, since they are the HDR videos a phone has. HDR frames keep no floor in the fixtures' parity, and `VideoFramesDeviceTest` with `-e video` and `compare_frames.py` compare one of the maintainer's clips. Another phone's decoder may tone map another way, and before Android 13 the platform may hand over HLG frames with no tone mapping at all. Decoding the raw 10-bit frames with `MediaCodec` and porting one tone mapping to both sides stays the way to the same pixels everywhere, at the price of a decoder of our own. An SDR frame keeps its values on both sides.
- *Parity.* `fixtures/videos/frames.json` holds, for each golden video, the lab's frames at the times of the rule: their embeddings, their mean red, green and blue, and their share of clipped pixels (a luma of 250 or more). `VideoFramesDeviceTest` takes the same frames on a phone. Each video must keep the frames at the lab's times, all of them for SDR and one a keyframe for HDR. An SDR frame must come within a cosine of 0.99 of the lab's embedding and within 3 levels of its mean colour. The 64×48 test patterns (`clip.mp4`, `ntsc.mp4`, `rotated.mp4`) get a floor of 0.96 instead, under `lowered_embedding_cosine` in `frames.json`: the phone gave 0.970 to 0.980 on them, with the mean within 1 level, and 0.9976 on the same pattern at 1280×720 (`hd.mp4`), so the gap is the two sides' chroma upsampling, which moves a large share of a 64×48 frame's pixels. Lowering the floor keeps the fixtures a few KB and their metadata as it is. `clip.webm` is in `phone_frames_may_not_read` (its metadata still has to read): the phone gives no exact frame of it, and a plain green one (0/135/0, YUV of zeros through BT.601) at its keyframe. A frame of one flat colour that is transparent, or green of 70 to 140 with no red or blue (what YUV of zeros gives through BT.601, BT.709 or BT.2020, 77 to 136), is what a decoder that output nothing hands over, so the phone fails the video on it, as on a missing frame. Black, and a brighter green, are frames. The cosine alone could not tell frames apart, since the frames of a one-second test pattern embed within 0.998 of each other, so `ramp.mp4` is four seconds of flat grays, one level a frame, with a keyframe a second: each frame's mean says which frame it is, and a keyframe would be up to ten frames off. An HDR frame has no floor, and is reported (above). A video that does not tag its color matrix gets the one Android gives it by size (`setDefaultCodecColorAspectsIfNeeded` in `ColorUtils`): BT.601 up to 720×576, BT.709 above. The lab picks the same, and `hd.mp4`, an untagged 1280×720 test pattern, checks it on the phone. Android takes BT.2020 for an untagged 4K frame, and the lab does not follow it there: no untagged 4K video is known, and no fixture checks it. The lab converts SDR with the rounding of the equations (swscale's `ACCURATE_RND` and `FULL_CHR_H_INT`); the second flag bypasses most of the tone mapping, so HDR frames go without it.

**In the app.** The build downloads the image encoder from the same revision, checks the same SHA-256 as the lab, and packs it in the APK's assets with Apple's license next to it. It is never committed. The app ports the lab's preprocessing step by step (Pillow's draft decoding, EXIF orientation, bilinear resize), and on the golden fixtures its embeddings match the lab's with a cosine of at least 0.99999. ONNX Runtime adds a 35 MB native library per ABI, so the APK only carries the arm64 one. On a Galaxy Z Fold7 (Snapdragon 8 Elite) the encoder takes about 47 ms per image on the CPU, the same at batch 1 and batch 16, and loading the model takes under half a second. A scan runs the encoder on the GPU, through ONNX Runtime's WebGPU execution provider, which the shipped ONNX Runtime build includes (#230). On the same phone that takes about 17 ms per image (batches of 16) and stays the same as the phone heats up, where on the CPU the time grows about 1.5 times. The embeddings match the CPU ones with a cosine of at least 0.999999. A phone or build without WebGPU runs the encoder on the CPU, and so does the rest of a scan once a run on the GPU fails, starting with the batch that failed: shaders compile, buffers are allocated and a device can be lost during a run, not only when the session is created. A crash inside the GPU driver kills the process and cannot be caught, which is an accepted risk. While the encoder runs on a batch, the next batch already decodes on the other cores, so memory holds at most two batches of pixels. An image that ran out of memory while decoding gets its retry alone, before the next batch starts: the text workers that run beside the embeddings (§7) wait for it too. With the encoder on the GPU this made the embedding phase about a fifth faster (5.5 s against 7.1 s for 300 images, #229). On the CPU it made no difference, because the encoder and the decodes share the cores. The text model stays on the CPU with one thread per worker: its phase already keeps every core busy, and on the GPU it ran about a quarter slower. Preprocessing takes 30 ms for a WhatsApp JPEG, 53 ms for a 12 MP camera JPEG (draft decoding does most of the work) and 280 ms for a 1080×2400 PNG screenshot, which has no draft mode. With the encoder on the CPU, that puts a 10,000-photo library at roughly 15 to 20 minutes on one core, less with preprocessing spread across cores. A PNG or WebP has no draft mode, and a 4320×7680 one holds the bitmap, an equal `IntArray` and a float plane at once, about 12 bytes a pixel, which can exhaust the heap. So a non-JPEG image above 16 megapixels decodes with a sample size (a power of two, the smallest that fits, even when a side ends under the draft side, so a 1080×30000 scroll capture fits too), and below that limit it decodes at full size, so the pixels the lab compares against do not change. The golden fixtures stay below the limit. A wide gamut image (Display P3) keeps its stored values, because Pillow ignores the profile and `getPixels` converts to sRGB: on a saturated synthetic image the two embeddings differed by a cosine of 0.9993, under the 0.9999 the lab parity asks for. This changes the pixels, and so the embedding, perceptual hash, blur, exposure, faces and text results, of every wide gamut image (Display P3, Adobe RGB), but no detector version is bumped, as a deliberate exception to the bump rule: the gap is a cosine of about 0.9993 and only on that subset. Results already stored for such an image keep the sRGB-converted values until the file or a version changes. An image sampled this way has android pixels the lab does not reproduce, which only a huge PNG or WebP can reach.

**Text coverage in the app.** PP-OCRv4 detection runs on the CPU with one thread per image, as in the lab, so the scan's workers do not fight over cores. The build downloads the model from the lab's pinned URL and SHA-256 and packs it as a resource. Pillow's draft rule asks for both sides to stay at least 640 px, so a 1600×1200 JPEG decodes at full size, where MobileCLIP's 256 px draft decodes it at a quarter. That is why text preprocessing costs more than MobileCLIP's (about 65 to 100 ms against 31 for a 12 MP JPEG, and 80 to 115 ms against 14 for a WhatsApp one; PNG screenshots have no draft mode and cost the same, 110 to 175 ms against 117). On a Galaxy Z Fold7, with a release-like (non-debuggable) build and a warm runtime, detection plus preprocessing takes 150 to 240 ms per image on one thread, and the model alone about 100 to 150 ms. With one image per core (8 threads) it runs 20 to 26 images per second, so text coverage adds roughly 6 to 8 minutes to a 10,000-photo scan. Loading the model takes about 0.35 s. The speed tests must be run on such a build: a debuggable build runs the Kotlin preprocessing about three times slower, and the first rounds after install run slower again while the runtime compiles the hot loops. Hence `TextSpeedDeviceTest` warms up before it times, and the MobileCLIP times above, from a debuggable build, are about twice too high for preprocessing (14, 31 and 117 ms for the WhatsApp JPEG, the camera JPEG and the screenshot on the same build).

## 6. Ranking

### 6.1 Candidate selection

An image becomes a candidate if **any** signal exceeds its category threshold (D4). Thresholds are tuned in the lab for recall (§10), and the values are in `ranker.py` and `Ranker.kt`. Those values are the defaults. On Android the user can override the threshold of each category in the settings, except one whose detector scores only 0 or 1 (§8), and the app builds its `Ranker` from the defaults with the overrides on top. The signals are already in the index, so a change applies the next time a list is built and needs no scan. A threshold equal to its default is not stored, so a retuned default still reaches the user. The lowest value is 0.05, because a best copy of a group has score 0 and no threshold may suggest it (§7). Raising a threshold takes images out of the candidates, which is the one way the user can trade recall for a shorter review, so the screen says so. Protection weights are not part of the setting, and kept and trashed images keep their review state whatever the thresholds are. The lab has no overrides: it ranks with the defaults, so the two sides stay comparable. Images with the same likelihood are ordered by the xxh3 hash of their path, not by the path. File names such as `IMG_20190101_...` hold the date, so ordering by path would list the oldest photos first among equals, and photo age is not a signal (D5). The hash is arbitrary but stable, the same on both sides, and drops or adds no candidate. A threshold can differ per media type (§5): `VIDEO_THRESHOLDS` holds the threshold of a category for videos where its video score is graded, today `BLURRY` (0.15), `BAD_EXPOSURE` (0.4) and `SHORT_CLIPS` (0.3), and the ranker holds a video to it, and to the shared threshold for every other category (the photos' slider cannot hide a video, and the video's cannot hide a photo). The user overrides each in its own preference, and the thresholds screen shows the two in sections of their own, "Photos" and "Videos" (§8). The lab has the same two tables, and its report for videos suggests thresholds for `VIDEO_THRESHOLDS` (§10).

### 6.2 Protection signals

These signals hint that an image is a memory: faces, favorites, membership in a user album, uniqueness (no near-duplicates). They lower an image's position in the review order but **never** remove it from the candidates.

They are ordinary `Signal`s whose category is a `Protection` (`FACES`, `FAVORITE`, `ALBUM`) instead of a deletable `Category`. They have no threshold, so they never make an image a candidate. The ranker multiplies an image's likelihood by `1 - weight × score` for each one. Uniqueness is not a signal: the ranker derives it from the image being in no duplicate or burst group. Candidates always stay ahead of the other images in the order. Favorites and albums only exist on Android (MediaStore), so the lab has no detector for them. On a video, `FACES` is the mean over its frames of each one's most confident face (§5, #394), with the weight of an image's. Only `FACES` and `FAVORITE` exist so far: the ranker has a weight for `ALBUM` (0.6), but nothing emits it yet, so an image in a user album is not lowered.

**The `STICKER` list is ordered by protection only.** Every sticker has the same likelihood, so its place in the list comes from uniqueness (a sticker in a duplicate group comes before one in none), a favorite on Android, and then the path hash (§6.1). `FACES` does not run on stickers (§5), because it was not shown to help this order: on the labels of #359, YuNet finds a face on 62% of the 69 kept stickers and on 59% of the 233 deleted ones, and the chance that a labeled delete comes before a labeled keep is 0.533 with `FACES` and 0.513 without, with a paired bootstrap interval for the change of -0.110 to +0.072 (95%). With so few keeps that rules out a large benefit, not a small one. Most of the faces found are probably cartoon ones.

`FACES` is an ordinary detector: it emits the signal, the index stores it, and its version applies, like any other signal. `FAVORITE` is not stored. The gallery changes it at any time, with no change to the file, so a stored copy would be stale as soon as the user hearts an image. `Review` asks MediaStore for the favorites each time it needs a ranking (one query for `IS_FAVORITE = 1` on the Images table and one on the Video table, a few dozen rows on a library of 1,000 images) and adds a `FAVORITE` signal of score 1 to those images in memory. The cached ranking is built again when the set differs, and the index and the detectors are not touched, so a scan has nothing to do for it. The same query runs again when the user applies a page. The user can also heart an image from the review's full size view (§8, #337): the app asks MediaStore through `createFavoriteRequest`, which takes `true` to add a favorite and `false` to remove one, and the system may show its own confirmation. A declined request changes nothing. The page on screen is not read again after an answer: the next ranking would move the image in the order, and a page that reshuffled under the user's finger would lose its marks and its place. The page keeps its images and marks, and only the heart of that image changes. The ranking built later reads the new set by itself, as for a heart made in the gallery. A favorite made this way is a favorite the user saw, so the dialog below has nothing to say about it unless they mark it for the trash. Reading `IS_FAVORITE` needs no permission beyond the one that reads the images, and `minSdk` 30 is where the column starts. An image the gallery hearted is still a candidate (D4): it only moves down the order.

**Videos get the same protection.** In a category (`EXACT_DUPLICATE` and `FORWARDED` today, #389, #391), a favourite video, or one with faces once #394 detects them, is lowered as an image is. In "Largest videos" (§6.5) a favourite keeps its place by size and shows a heart (§8, #387). The full size view of a video has the heart button of an image (#441), which asks the system to mark or unmark it, so the user can protect a video from the viewer; the ranking reads the new mark with the other favourites at its next build. Trashing a favourite video asks first, by the rule below, on every page of videos, "Largest videos" included: when the selection holds a favourite, the main button opens the dialog before it moves anything to the trash. A video that the gallery hearted after the list was read is not trashed unasked either: the apply reads the favourites again, shows the list with the new heart and the same selection, and says why in a snackbar.

**Trashing a favorite asks first.** The review marks a favorite with a heart (§8), and does not preselect it for the trash, even when it is a candidate: it stays in the candidates and in its place in the order, so recall is unchanged, but the user has to mark it. When the user marked a favorite on the page, the main button opens a dialog before applying it (D6), which says how many of the images are favorites, and its button reads "Move to trash anyway", in the error color. Cancelling trashes nothing. A page with no favorite marked applies at once, so trashing the similar copies of a favorite stays as quick as before, and a favorite the user kept on the page is not mentioned. The favorites the dialog named are the ones the page showed. If the gallery marks another marked image as a favorite while the page is open, applying finds it at that moment, trashes nothing, and shows the page again with the new heart and the marks the user had, so the next dialog names it. A snackbar says why ("An image became a favourite meanwhile. Check the page.", #329), since a page that comes back with nothing trashed looked like a failed tap. Faces come from [YuNet](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet), a 230 KB ONNX face detector under the MIT license. Like MobileCLIP, the same file runs on ONNX Runtime in the lab and in the app, so ML Kit is not needed for faces. The lab commits the file, and the app build copies it from there instead of downloading it.

### 6.3 Review state

Each image carries a review state:

- `UNREVIEWED`: candidate as usual.
- `KEPT`: the user reviewed it and chose to keep it. It is not suggested again unless a **new** signal appears. For example, a higher-resolution copy shows up and turns this one into the inferior duplicate. Keeping an image records the identity of each signal it has (category, group, role). A take's identity is its category alone (§5), so a kept take never comes back as a take. Keeping also records which detectors had stored a result for it. The first result a detector stores for a kept image after that, such as `DOCUMENT` after a keep during the first scan, or a group detector on an image first seen in phase 1, is recorded as seen too: the image has nothing of that detector to be new against. Its later results count as before, so a group that forms or a role that changes after the first result is still new. A signal is new when its identity is not among the recorded ones: a newer detector version, a higher score or a retuned threshold is not new.
- `TRASHED`: in the app trash.

Videos use these states too (#387), with the same rules: a kept video comes back only with a new signal. "Keep" on a video records the signals it has, as on an image.

**Excluded folders** are a second user decision, kept apart from the review state because it covers a folder instead of one image. The index stores a list of folder paths. The ranker leaves out every image under one of them, like a trashed image, and so does the review screen: those images are in no category, no count and no group. The storage map leaves them out too (§8). Detectors still run on them and the index keeps their signals, so their duplicates still count and removing an exclusion brings the images back at once, without a rescan. An exclusion never touches a review state: nothing marks an excluded image `KEPT`, and nothing trashes it. Excluding a folder covers its videos as well as its images: the map and "Largest videos" both read the index through the same exclusion (#386, #387). The two rows in Settings do not: they count the excluded folders too (§8).

- An exclusion covers the folder **and its subfolders**. A folder is a subtree to the user (`Pictures/Family/2020` belongs to `Pictures/Family`), and excluding each subfolder by hand would be tedious. A sibling that only shares the name prefix (`Family2`) is not covered.
- A duplicate or burst group with a copy in an excluded folder is still offered for the copies outside it. The excluded copy is not listed in the group, so "keep best, trash the rest" never trashes it, and it is not marked `KEPT`. When the excluded copy is the best one, the group shows the other copies without it, and they can still be trashed, since the excluded copy stays as the survivor. A group whose only candidates are excluded is not offered at all.

### 6.4 "Review everything" mode

All `UNREVIEWED` images, ordered from most to least likely deletable. Going through all of them eventually brings false negatives to zero by construction. A missed image just shows up later in the order.

It is an image mode, and lists no video. Videos have "Largest videos" instead (§6.5).

### 6.5 "Largest videos" mode

Every video the user has not reviewed, flagged or not, largest first: every `UNREVIEWED` video outside the excluded folders (`Review.largestVideos`, #387). Equal sizes are ordered by path, so age plays no part (D5). Like "Review everything" it is a list, not a detector signal, so it works before any video detector exists and drops no video (D4). On the maintainer's phone the 100 largest videos hold 42.6 GB of the 59.8 GB, and the 22 videos over 500 MB hold 22 GB (#387).

A kept video leaves the list, and comes back only under a category with a new signal (§6.3). A trashed one leaves it as well. A favourite keeps its place by size (§6.2). A video that cannot be read stays in the list, and the detectors skip it (§8). The list reads the gallery's favourites each time, as the review does, so a heart made in the gallery shows at the next read. A heart made from the full size view (#441) changes the flag of the video on the list in place, with no new read, so the list keeps its order and its selection.

### 6.6 Size in the order of a video category

In a category's list, a video's score after protection is multiplied by its size in bytes (`Ranker.by_category` in the lab, `Ranker.byCategory` in the app, #397). Of two videos with the same score and protection the larger comes first: one deleted 900 MB video frees more space than a thousand images, and `FORWARDED` and `TAKES` score every video 1, so before this the order inside them was only the path hash. Protection still only lowers a video, by the same factor as before, and size drops no candidate and adds none (D4). Age plays no part (D5). An image's size plays no part either, so the images of a category keep their order exactly. The likelihood `rank` gives a video does not change, since no list orders videos by it: "Review everything" lists images only (§6.4), and the lists of a category are sorted again here. Equal products keep the order of `rank`, so the order of `rank` (likelihood, then the path hash) breaks a tie. A video of 0 bytes counts as 1, so it keeps its score and protection order. A list's order holds only within one media type, since a video's key is in bytes and an image's is not, and the app never shows the two in one list. The decisions:
- *A factor, not a tie-break.* A tie-break would order by score and protection first and use the size only between equals. That is the order today, since every video scores 1, but once #394 gives graded scores a difference of 0.01 in a score would outweigh a video a hundred times larger, and the issue asks for the larger of two flagged videos first.
- *Not a sort the user picks.* "Largest first" (§8) already sorts any category, the Videos tab's included, by bytes alone. The suggested order is the one that changes, since it is what the user sees first.
- *Linear in the bytes, for now.* If the score after protection were a calibrated chance that the user deletes the video, the product would be the bytes a review of it frees on average, which is what the GB found in the first reviews measures. It is not calibrated today: `FORWARDED` and `TAKES` score every video 1, and the protection weights are picked by hand (§6.2). So while the scores are flat, the suggested order of a video category is about the same as "Largest first", and protection is only a nudge: a favourite (a factor of 0.2) of 1 GB comes before an unprotected video of 150 MB. It is still a candidate either way, shown with its heart and not preselected (§6.2), so the user has to mark it. The shape (linear, square root, logarithm, or calibrated scores) is to be checked again once the labels hold protected videos. Graded scores came with #394 and #395, and the bytes still outweigh them: a short clip scores 0.3 to 0.95 and weighs 0.3 MB to 640 MB, so the order of "Short clips" is about the order by size (§5, #395).
- *On the labels of #390.* Only `FORWARDED` flags labeled videos so far: 30 of the 50 in the lab's index, 0.19 GB, with 23 labeled deletes (0.124 GB) and 6 keeps. By size, the first 5 reviews find 0.084 GB of deletes and the first 10 find 0.102 GB, against 0.021 GB and 0.041 GB for a random order on average (0.009 GB and 0.013 GB for the path hash on the lab's paths). The GB gain has a price in the keeps: the larger chat videos were kept more often (the kept ones are 2 to 37 MB, the list's median is 1.8 MB), so by size a labeled delete comes before a labeled keep only 0.19 of the time, against 0.5 for a random order on average and 0.28 for the path hash. The first 10 reviews show 4 keeps both by size and by the hash. Over all 49 labeled videos, as if every one were flagged, the way the camera detectors still to come would flag camera videos, the first 10 by size find 1.42 GB of the 1.68 GB of deletes, against 0.34 GB for a random order on average. The study is `lab/scripts/study_video_size_order.py`. It opens the index and the labels read-only and runs the video detectors that read no frame in memory, since the lab's index holds no video signal yet, and prints aggregate numbers only.

## 7. Architecture

The core idea is a pipeline of independent, interchangeable components.

The block below uses the names decided for videos (#382). The `images` table, `ImageIndex` and `ImageMetadata` keep their names, and so does every name that is about images only, such as the decoding, the tiles and the Compress page. The media type is `MediaType` and a detector's declaration is `mediaTypes` (`MediaType` and `media_types` in the lab), as #382 sketched them (#383): they match the `media_type` column, and `Kind` was taken. `MediaRef` carries the media type, so a source hands it to the index with the file and a step can filter on it.

```kotlin
enum class MediaType { IMAGE, VIDEO }   // the index's media_type column, and MediaRef.mediaType

interface MediaSource {                  // MediaStore + deep scan today; cloud libraries later
    fun scan(): Flow<MediaRef>
}

interface Detector {                     // one per technique; a cloud classifier would be one more
    val id: String
    val version: Int
    val category: Category? get() = null
    val mediaTypes: Set<MediaType> get() = setOf(MediaType.IMAGE)   // the pipeline gives it only these
    suspend fun analyze(media: MediaRef, context: AnalysisContext): List<Signal>
}

interface GroupDetector {                // duplicates, bursts: looks at all images or all videos at once
    val id: String
    val version: Int
    val category: Category? get() = null
    val mediaTypes: Set<MediaType> get() = setOf(MediaType.IMAGE)
    suspend fun analyze(media: List<MediaRef>, context: AnalysisContext): Map<MediaRef, List<Signal>>
}

enum class Role { BEST, INFERIOR, TAKE, SHORT_TAKE }   // a group member's role, stored in evidence["role"]

data class Signal(
    val detectorId: String,
    val detectorVersion: Int,
    val category: Category,
    val score: Float,                    // 0..1
    val evidence: Map<String, String> = emptyMap(),
)

interface Ranker {                       // combines signals into candidates and an ordering
    fun rank(media: List<IndexedMedia>): List<Candidate>
}

interface Trash {                        // app-managed trash, retention set by the user (30 days by default)
    suspend fun moveToTrash(media: List<MediaRef>): List<TrashedImage>   // the item each file became
    suspend fun restore(media: List<MediaRef>): List<MediaRef>
    suspend fun trashed(): List<TrashedImage>
    suspend fun purge(media: List<MediaRef>): List<MediaRef>   // returns what it deleted
    suspend fun purgeItems(files: Collection<File>): List<MediaRef>   // exactly these items, by their file in the trash
    suspend fun purgeExpired(): List<MediaRef>
}

interface ModelRuntime                   // ONNX Runtime behind one interface
```

- Signals are stored with the version of the detector that produced them. When a detector improves, only its signals are recomputed.
- The pipeline runs in this order: scan, metadata, the per-image detectors that read no embedding (with the perceptual hash), the embeddings with the per-image detectors that read one, then the group detectors. On Android those detectors run beside the embeddings (#357): the images whose embedding is stored already go to them first, and each batch's images as soon as the batch's old results are forgotten and its embeddings stored, so a result never reads an embedding other than the stored one. The encoder runs on the GPU, and while it still has batches to embed two of the workers are held back, so its decodes find two free cores ahead of the text coverage. Once the last batch is stored, every worker classifies. The two steps keep their own times in the scan log (`embeddings` until the last batch is stored, `embeddedDetectors` after it), so their sum is the time of the phase. Their bookkeeping (the run's failures, counts and progress) runs on one thread. A stop while both run keeps what each had stored: the embeddings of the batches stored, and the results stored, each with the embedding it read. The batch the model was on when the stop came is lost, and so are the finished results still waiting to fill their batch of 32 (§4), up to 31, which the next scan classifies again. If the stop fell between forgetting the old results of the model's batch and storing its embeddings, the next scan embeds those images and classifies them again. The lab runs the two steps one after the other, with the same results. Each step stores its results as it goes, so the home screen lists candidates from the first detectors on, and an interrupted pass resumes. Images in a sticker folder come after the real images in the metadata step and the first detectors, run only the perceptual hash, `SCREENSHOT` and `STICKER` among those detectors, and skip the embedding and the detectors that read it (§5).
- Each step takes only the media types its detectors accept (§5), and a normal scan runs no step on a video (§4). A group detector gets the files of its media types and its fingerprint covers only those, so recording a video does not run the image group detectors again. A run that takes both runs every image step first, the image group detectors included, and then the video steps, so its progress shows the image phases and then the video phases as a second run (§4, decision 22 of #382). The group detectors that accept videos are built (#389): the video steps run them after the metadata and the frames, in the phase "Finding copies and takes". The frames of the videos (#393) are a video phase after the video metadata (§4), and the video group detectors stay last among the video steps, so they can read the frames. Each group detector runs on the images and on the videos apart, each run with a fingerprint of its own, so a group never mixes them. The scan log names the video run `<id>:video`, so a night pass that runs both tells them apart. The video group detectors read the stored video metadata (`videoMetadata` in `AnalysisContext`, `video_metadata` in the lab) and each video's stored frames, in the order of their times (`frames`). The model, its version, `FRAMES_VERSION` and the number of videos with frames join the video run's fingerprint, as the embeddings do for the image run, so frames stored after a run run the video group detectors again. So does the number of videos with a capture instant, so a capture time read again, as by a migration, runs them again although no file changed. The video group step reads the metadata of every video in one query (`allVideoMetadata`, `all_video_metadata` in the lab), as the image step does. The image run's fingerprint does not change. `SHORT_CLIPS` reads two more things (§5, #395): the stored measures of the videos' frames (`frameMeasures` in `AnalysisContext`, `frame_measures` in the lab) and the photos in a camera folder with a capture time, with their embeddings when the run has a model (`photos`). A group detector that reads more than its files may add an input key of its own to its fingerprint (`inputsKey`, `inputs_key`), so a new photo runs `SHORT_CLIPS` again and not `NEAR_DUPLICATE`, `TAKES` or `EXACT_DUPLICATE`, whose input did not change. The key of `SHORT_CLIPS` holds the versions of `TAKES`, `BLURRY` and `BAD_EXPOSURE` and three counts, taken with queries that load nothing: the videos with measures, the camera photos and those with an embedding. When the key is the same the detector loads none of it. When it runs, it takes the capture times of the clips under the gate from their metadata, reads the path and capture time of every camera photo (no embedding), keeps the photos within the window of one of the clips, and loads the embeddings of those photos only. The measures load on the first video that needs them.
- A detector that reads embeddings says so (`usesEmbeddings`). That flag also puts it after the embeddings in the order above, so a detector that reads one without saying so runs before any exists. Its embedding lookup then throws something other than `MissingEmbedding`, so it lands in the run's failures on every pass instead of waiting for an embedding that its pass never gets. A result belongs to the embedding it read, so when the pipeline computes an embedding for an image it forgets that image's results from those detectors.
- A failed embedding is a failure of that image, not of the scan. The image gets no embedding, its failure goes into the run's failures, and the next run tries it again. An image that ran out of memory while decoding gets one more try alone, after its batch, since other decodes may have taken its memory. The scan always goes on to the detectors, so one bad file cannot keep DOCUMENT and FORWARDED from running on the others. The failures of the last finished run are kept for the settings screen (§8). A detector or a perceptual hash that runs out of memory while several images are analyzed at once runs again alone, after the others, and fails only if it fails then too.
- Detectors get per-image data they don't compute themselves (content hash, metadata, embeddings, decoded pixels) through lookups in `AnalysisContext`. The pipeline backs them with the index, so each value is computed once and shared by every detector.
- Decoded pixels are not stored. The pipeline gives the detectors of one image, and its perceptual hash, one memo (`Pixels`) that lives as long as the image's task: a sample size decodes once, the EXIF orientation is read once and the grayscale at a side is computed once (#353). A decode depends on its draft side only through the sample size it gives, so a detector gets the pixels its own decode gave it and no output changes. The memo keeps only its last decode, so memory holds one decoded image, as when each detector decoded its own. A detector says the draft side it decodes at (`decodeSide`), and the pipeline runs an image's detectors from the largest side down, so the sides that give one sample size come one after the other: `FACES` (640), `BLURRY` (512), `BAD_EXPOSURE` (256), then the perceptual hash, which reads exposure's grayscale. A sticker, a PNG or a small JPEG decodes once, and a JPEG at most three times, against four decodes and four EXIF reads before. The order of `DETECTORS` itself stays, since settings lists the steps in it. The lab has the same memo, order and `decode_side`, but Pillow decodes the grayscale straight from its own `L` draft and the faces from an `RGB` one, so there the memo shares only the grayscale at one side, which exposure and the perceptual hash both load at 256.
- Group detectors (duplicates, bursts) run over the index instead of over a single image. They use the same `Signal` output. Every member of a group gets a signal, with the group id in `evidence["group"]` and its role in `evidence["role"]`: `best` for the copy to keep (with score 0, so no threshold ever suggests it), `inferior` for the others. A group of takes has no copy to keep, and its members are `take` or `short_take` (§5). Images in no group get no signal.
- `NEAR_DUPLICATE` never links by hash two images whose pHash is 0 or has only the DC bit set. A uniform image gives one of the two, since every AC term rounds to 0: black hashes to 0 and any other flat image to the DC bit, so they all sit within a bit of each other. A few simple shapes, such as a white image with a dark band over its left or top eighth, give the same hash and are treated the same way. Such a member says `evidence["flat"] = "true"`. It can still join a group through its embedding, and a uniform image is also a `BAD_EXPOSURE` candidate either way.
- `BURST` chains shots by time and embedding, comparing each shot with the last shot of the current burst. When it does not follow, it starts a possible new burst, and if the next shot follows the last shot of the first burst instead, the shot between is dropped as one different frame. Without this, A, B (another subject), C (like A) would split into three singletons, and one different shot would destroy the burst. The 3 s gap is measured from the last shot of the burst, so shots 2 s apart can chain for longer than 3 s in total. The best shot is the sharpest by the BLURRY measure (the variance of its sharpest region), rounded to one decimal as `BLURRY` stores it in its evidence. The group phase reads that stored value instead of decoding every member of every burst again, and decodes a shot only when it has no `BLURRY` result, such as after a failed blur run. Rounding on both paths makes them rank shots the same. The group fingerprint includes the `BLURRY` detector's id and version, so a new blur version reruns the group detectors even when no file changed.
- The Python lab mirrors these interfaces one-to-one, so porting is mostly translation.

**The capture time of a video.** An MP4 stores its creation time in UTC, and an image's EXIF time is the camera's local time with no zone. `captured_at` stores local time for both: a video's UTC time is turned into local time with the zone the phone is in when the video step reads it, at the rules of that instant, so a winter clip read in summer gets the winter offset. The lab does the same with the zone `scan --zone` names, the machine's own by default, and it warns when that zone is UTC, as in a container or on a fresh VM, where every clip would land hours from the photos beside it. Two `captured_at` values then compare as two wall clocks, which is what the photo taken beside a clip (#395) needs. The takes (#392) compare one clip with another, so they read `captured_instant` instead (§5). The limit: a clip recorded in another time zone than the one the phone is in when it reads the clip moves by the difference, while a photo of the same trip keeps the trip's local time. So a photo and a clip taken together abroad and read at home are hours apart in `captured_at`, and a clip's value depends on where the phone was when it read the clip. So a video also keeps the moment itself in `captured_instant`, as epoch milliseconds in UTC, which no zone moves, and #395 can match instants when a photo has `OffsetTimeOriginal`, which Pixel and Galaxy cameras write. An image leaves the column empty for now, and can fill it when a detector needs it: the column came with the version 8 migration, so that needs no other. Storing UTC alone was the alternative, and it needs an offset for every image, while screenshots and messaging apps write none. A camera that writes local time in the MP4, against the format, is shifted the same way in both columns. A time before 1971 is a camera with no clock, whose zero is 1904 or 1970, and counts as no time in either column. A Matroska or WebM date is not read, since Android's extractor does not give one, so the lab leaves it out too. Nobody has checked yet what a Galaxy writes in the creation time of its clips.

A single finger on a photo at rest still scrolls the summary. **The zoom shows real pixels** (#299). Coil draws each photo at up to 2,048 px on its long side, and once the zoom needs more than that, `TiledImage` decodes the part on screen again with `BitmapRegionDecoder`, cut into tiles of 512 decoded pixels, at the largest power of two sample that still gives each screen pixel at least one pixel of the file. Both layers share one `Zoom`, the same region and scale, and each reads its own file at its own resolution, so at the original's 100% a copy at Smallest shows its own pixels four times larger. The zoom goes up to twice the original's full resolution, so single pixels and JPEG blocks show, and the image's state description says it as a share of that resolution ("Zoom: 3% of full resolution" at rest on a 200 MP photo on the summary's slider, 100% at one screen pixel per pixel), for a screen reader: the line under the photos, the "Before and after" heading and the paragraph about the gestures left the screen in #321, and the gestures are in the image's description. A tile is read in the file's own pixels and drawn turned by the EXIF orientation, the same turns as `Imaging.transpose`. **One decode per view.** Since Android 7 a JPEG region decode goes through Skia's JPEG codec with no index of the file, so every `decodeRegion` reads every row above the region at full width, and a coarser sample saves only the inverse DCT. A region at the bottom of a 200 MP photo costs about a whole pass over the file, whatever its size. Measured in the review of #303 with libjpeg-turbo's crop on a synthetic 16320 × 12240 JPEG at quality 90, on one laptop core: one tile at the top took 29 ms, in the middle 300 ms, at the bottom 510 to 600 ms, and a full-width strip at the bottom the same as one tile. A full screen at 2 times, 30 tiles, took about 9.8 s read one by one and about 0.6 s as one call. So `TileLoader` reads the bounding box of a view's missing tiles in one decode and cuts it into the grid, and the box, which is never drawn, is recycled. A box over 100 MB of decoded pixels is read a row of tiles at a time instead, the row nearest the centre first, since a decode and its copies would hold twice the box; neither the panels nor a phone's full screen come near it. Only the tiles that cover the view are kept: each change of zoom or position drops the others (left to the garbage collector, not `recycle()`d, since the render thread may still draw the last frame) and decodes the missing ones off the main thread. When the zoom crosses a power of two, a tile of the old sample stays, drawn under the new ones, until the new tiles over it are in, so the base image never shows in between; that holds up to twice the tiles during the switch. The decoded pixels on screen stay under twice the view on each side, plus a tile at each edge: about 14 MB for a 500 × 375 px view, and about 75 MB for a full screen of 1080 × 2340 px, whatever the photo's size. The slider's layers are as wide as the summary, about 1,000 × 750 px on a phone, so each holds roughly 25 MB and the two 50 MB, scaled from the 14 MB figure by the area of the tile grid and not measured. Only the photo on screen has layers: a photo on another tab holds no tiles. These figures leave out the GPU's copy of each drawn tile, the box while it is cut and the tiles waiting for the garbage collector, so real use is about twice that. It still fits next to the preview's own encode of a 200 MP photo (1.44 GB at High quality on the Fold7, §9), and neither layer decodes a tile until every preview of the summary is made or has failed, so a zoom during an encode does not slow it, nor takes the memory its check counts on, and only the base image shows. With three 200 MP photos the user waits for all three encodes before the zoom shows real pixels. A view whose decode fails, out of memory included, drops all tiles and leaves the base image; the next change of zoom or position tries again. Leaving the summary cancels the tile work, waits for the decode in progress and closes the decoder, which held its own descriptor of the file: the preview file is closed a decode after it is deleted, not left open. `BitmapRegionDecoder` won over a library such as Telephoto (`zoomable-image-coil3`), which does subsampled tiles on top of Coil: it is in the platform, the two panels must share one zoom and keep the summary's own gestures (one finger at rest scrolls the summary), and #300's slider needs one source clipped to a region, which a `TiledImage` under a clip does. A library would bring its own gesture and state model to bend around all three. Robolectric checks the tile region, the orientation, that an original and its half-size copy show the same part of the photo, the zoom math, and the loader against a fake decoder: one decode per view, rows centre first, the old sample kept until covered, the retry after a failure and the close. It also decodes one real region. For the comparison it checks the choice of photos, that the previews run one at a time and in order, that the first shows before the others are made, that a refused one does not stop the rest, that closing stops the ones not started and that every file is deleted, the tabs and the descriptions that read their sizes, and the slider's gestures (the handle moves the line without panning a zoomed photo, a finger elsewhere pans or leaves the drag to the summary, a pinch with a finger on the handle zooms, the tick at each edge) and its semantics (description, range and the increment and decrement action). It cannot see the clip, so that the copy shows only to the right of the line is left to the phone. What it cannot check stays with the phone: how long a view takes on a 200 MP file (about one pass over the file down to the bottom of the view, so a view low in the photo waits longest, and a progressive JPEG has to be read whole for each decode, with memory for all of its coefficients, which a camera does not write but another app may), whether seams show between tiles, and how the switch from the base image to the tiles looks. - **Short clips loop in the grid** (#398). Deciding on 200 short clips one full size view at a time is slow, so in the "Short clips" review a tile on screen plays its clip, muted and in a loop, over its frame, as a GIF would, and the user decides at a glance. Only the first `LOOPING_CLIPS` (2) readable tiles on screen play, in the grid's order, since each player is a hardware decoder and a phone runs only a few at once. The real limit has to be found on the phone, by measuring the scroll with the tiles playing (`android/scripts/measure.sh`). Nothing plays while the grid scrolls: a scroll releases the players, and the tiles on screen start once the grid settles, so a fling builds and releases no player for each row it passes (`ExoPlayer.release` runs on the main thread and can wait up to 500 ms for its codecs). The limit counts places, not players. A scroll empties every place before any is filled again, but when the tiles that play change without a scroll, as when a page replaces the last one, each tile is a composition of its own, and a new tile's player can be built in the same frame before an old tile's is released, so for that frame one more player may run. Each loop is a `VideoPlayback` of its own, muted from its first frame, so it never takes audio focus (#418), with its audio track turned off, so it takes no audio decoder nor `AudioTrack`, and with no handling of headphones coming out, since it has no sound. It draws on a `TextureView`, not the full size view's `SurfaceView`, since a `TextureView` moves with the scroll and is clipped to the tile, cropped as the frame is. - **How the grid tiles are decoded** (#349). The tiles of the review, the Compress page and the trash load with the decoders Coil's default loader picks on Android 10 and later (`StaticImageDecoder`, which is `ImageDecoder`, and `BitmapFactoryDecoder` when it does not apply), under a limit of their own: the number of cores minus two, from 2 to 6 decodes at once (`tilePermits`, 6 on an 8 core phone). Coil's default is 4 for every image of the app, and the 30 tiles of a Compress screen queued behind the 4 largest files (3.1 s to the last tile, #342). A tile decode is small in memory, its bitmap of 0.4 to 0.8 MB plus libjpeg's row buffers, so six at once cost a few MB. The full size views and the summary's before and after keep Coil's default 4, since one of their images can be 12 to 50 MB. Only the number of decodes at once changes: they are the same decoders with the same options, so the tiles draw and cache as before. A more parallel decode competes with the UI and render threads for the cores, which is why the limit leaves two cores and why the scroll jank is measured with it (android/README.md).
- **The grid tiles' disk cache** (#351). Coil keeps no disk cache for local files, so each process start decoded every tile on screen from its original again, and the first Compress screen, which lists the largest photos, was 10 to 12 s of CPU work for 15 tiles (#360). `TileCache` keeps the bitmap a grid tile decoded (review, Compress and trash) as a JPEG at quality 85, about 30 to 40 KB, and the next load of that tile decodes the JPEG instead of the original. The key is the path, the file's length and modification time, and the tile's size in pixels with Coil's scale and precision. An edited file misses, a compressed copy misses (it keeps the path and the time, §9, and has a new length), and a tile of another size, as on the other screen of a foldable, gets a thumbnail of its own. A thumbnail decodes to the same bitmap size the original did, and is marked sampled as the original's decode was, so Coil's memory cache never serves it to a full size view. The full size views do not use the cache. It holds only files of 1 MB or more, since a smaller one decodes in a few ms and would push larger ones out, and only sampled, opaque bitmaps: an image no larger than the tile gains nothing, and a JPEG has no alpha. A miss decodes in software, stores the JPEG once the decode has given its permit back, and hands the tile the hardware bitmap the request asked for, because encoding a hardware bitmap needs a copy back on the render thread. Coil's `DiskCache` does the eviction, least recently used first, past a cap of 32 MB (about 900 thumbnails): the app deletes none of the files itself, and the trash stays the only code that does (§9). The cache is `tiles` in the app's private cache directory, so Android's "Clear cache" empties it and the cache line of the storage section counts it. Coil hashes each key into the file name, so no path is written to disk. These are thumbnails of personal photos: they stay in that directory, and no log line or trace section names a file.
- **Preparing the tiles after a scan** (#351). A scan that runs to its end enqueues `TilePrepareWorker`, its own unique WorkManager work (`tile-prepare`, replacing a pending one, with the battery not low), once the scan's lock is released. It loads the first two Compress pages, 100 photos, largest first, so the files over 8 MB that hold most of the decode time come first. It runs one photo at a time on a thread of background priority, at the size of the last Compress tile, which the cache remembers, so its thumbnails are the ones the page asks for; before the page has shown a tile it does nothing. A thumbnail the cache holds is skipped, and nothing goes to the memory cache. Between two photos it stops when a scan starts (the scan's end enqueues it again) or when the heat is moderate or worse (§4), and it gives way to a compression batch, which WorkManager retries a minute or more later. It reads the index and touches no signal, ranking or file of the library.
- **How the full size views load** (#350). The Compress page was blank for 0.7 to 0.85 s when a large photo opened (`TiledImage.base`, #342), the base image being the entropy decode of the whole file, and the next photo was only requested when a swipe landed on it. Three things change, and none of them touches a tile, a score or a compressed byte. **The base image** is requested at 2,048 px on its long side, fitted, with Coil's inexact precision, so a decoder only scales down: a 200 MP photo of 16,320 by 12,240 px gives a 2,048 by 1,536 bitmap of 12 MB with `ImageDecoder` and with `BitmapFactory` alike, a small photo is not enlarged, and `BaseImageTest` checks it. (#342 assumed Coil would pick sample 4 and a 4,080 px bitmap of 50 MB; it does not, so the base was already this size and its decode time is the file's, not the bitmap's.) `visibleTiles` starts the tiles where a sample would be finer than that base, so the zoom still reaches the photo's own pixels, at two screen pixels for each, and the same test walks the zoom of five photo sizes to check it. **The grid tile is the placeholder.** A tile is stored in Coil's memory cache under the key `tile:<path>:<length>:<modification time>`, the parts of its disk key, since a compressed copy keeps the path and the time and only its length changes, and a full size view (the Compress one, the review's and the trash's) looks that key up when it opens and draws the tile, upscaled and blurry, until its own image arrives, so the view shows pixels at once if the grid still holds the tile. Coil 3 keeps the size, scale and precision out of an explicit key, so the lookup needs none of them; if the tile is gone the view is blank until the image arrives, as before. **The next photo is prefetched.** When the base image of a Compress photo shows, the base of the next photo of the page is requested behind it (`TiledImage.prefetch`), so a swipe lands on a decoded image. It starts after the shown one, because both at once would slow the one the user waits for. It outlives the page, and a swipe that lands while it still loads waits for it instead of decoding the photo a second time (Coil does not join two requests for the same image); closing the view stops it. Only the next one is requested; the one before is still in the cache if it was shown. **The full size views have a memory cache of their own** (`FullSizeLoader`: Coil's loader with a 40 MB cache, about three bases of 12.6 MB), used by the three full size views and by the summary's before and after, and emptied when they close, but not on a rotation or a fold, which recreate the activity and keep the view open. Coil drops the least recently used image when its cache is full, and under a full size view that is a tile of the grid behind it: with one cache, a few bases could evict most of a Compress screen, and Back would queue its tiles again for seconds. The default cache now holds tiles only, so Back finds the grid as it was. The cost is up to 40 MB of memory while a full size view is open.

## 9. Deletion and trash

The system trash (`MediaStore.createTrashRequest`, Android 11+) only works for files MediaStore indexes, so it misses `.nomedia` folders. Cribrum therefore keeps its **own trash**: files move to an app-managed folder together with their original path, and are purged after a retention the user sets in the settings screen: 7, 14, 30, 60 or 90 days, 30 by default. One mechanism covers every file.

The trash is a `.cribrum-trash` folder at the root of each storage volume, with a `.nomedia` file so galleries skip it. Each trashed file gets its own folder there, holding the file under its own name and an `origin.properties` with its original path, size, mtime, media type (`media_type`, `image` or `video`: an item written before #385 has none and reads as an image, and so does one with a value this build does not know, such as one a later build wrote, so a downgrade never hides an item from the screen and the retention), the time it was trashed (`trashed_at`), when the trash first saw it (`seen_at`), and `favorite=true` when the gallery had the image marked as a favourite at that moment (see The favourite flag). Moving is a rename on the same volume: it is instant, and it keeps the mtime, so a restored file is the same `MediaRef` as before, media type included, since `MediaRef` equality compares it. Moving refuses a file named `origin.properties`. Because the trash lives on shared storage and needs no database, it survives an uninstall and can be restored by hand. A file that changed since its scan is not trashed, and a restore uses `Files.move` without replacing existing files so it cannot overwrite a file that took the original path. The trash is the only code that deletes files. The retention is read on every purge, not stored with the item, so a change applies to the items already in the trash too: lowering it purges what is now older than the new value at the next scan, so the settings screen first asks for confirmation, with the number of images that would go, when the new value would purge at least one. A purge needs the trash to have seen the item for the whole retention: both `trashed_at + retention` and `seen_at + retention` must be at or before now. Moving writes `seen_at` with `trashed_at`, and the purge writes it for items that lack one. When the system clock is before `seen_at`, the purge rewrites `seen_at` to now, so turning the clock back does not shorten retention. Reading a trash item treats a `trashed_at` in the future as now, and skips corrupted or truncated records without failing. The trash purges an item once both retention checks pass, or when the user deletes it for good from the trash screen.

The trash screen (#321) shows each image with its days left, under a hint that says how to select and how to see an image full size (#329: Settings already says how long the trash keeps images). A tap selects it, with the check badge of a selected Compress tile, since a border alone disappeared on a purple or dark photo. A long press opens it in the same full size view as the review, with its folder, its days left and the heart of a favourite, so the user sees a photo before restoring or deleting it, and a "Selected" checkbox at the top right that selects it as a tap on the tile does (#329). With nothing selected, "Empty trash" is the only button, outlined and in the error color, because a wide disabled "Restore 0" outweighed the one action there was (#329). Once something is selected, Restore is the filled button, and "Delete 3", for the selected images only, is a text button in the error color beside it, so it weighs less. The selection holds trash items, by their file in the trash, not original paths: an original and its compressed copy share a path, and so can a file trashed twice. `AppTrash.purge` deletes one item for each image it is given, so two items that are the same image go only when both are asked for. Its dialog says how many images it deletes and how much space that frees ("This frees 412 MB and cannot be undone."), with its confirm button in the error color, and the images go through `Review.purge`, the trash's own purge. The screen opens at once, empty under the app's progress bar, and fills when the list is read (#352): a trash of several hundred items takes about a second to read on shared storage. It says the trash is empty only once the list is read. `AppTrash` reads the item folders six at a time, since each read waits on the file system, and sorts them by `trashed_at` as before.

**Videos in the trash** (#385). One trash with one retention holds images and videos, and a video moves, is restored and is purged like an image. Its item records `media_type=video`, so the trash rebuilds the same `MediaRef` when it checks the file before a move and when it reads the item for a restore or a purge: with the image type, the move refused every video and a restore or a purge matched none. Moving stays a rename on the file's own volume in both directions, never a copy, since a video can be 900 MB. A move is `File.renameTo` into the trash of the volume that holds the file, which never copies. A restore uses `Files.move`, which copies and deletes when the target is on another file system, so it puts an item back only on the volume whose trash holds it: an item whose recorded path names another volume, such as a trash folder copied by hand, stays in the trash. Tests check that a video keeps its inode through a move and a restore, on the main volume and on a second one. How long a move of a 900 MB video takes on the phone was not measured. The trash screen lists videos in a section of their own, between the images and the stickers. A video's tile shows a frame (Coil's `coil-video`, at the version of the Coil in the build, with its decoder set on the request, so a frame does not depend on the file's extension), its length and its size, and its description says them to a screen reader. The length is read with `MediaMetadataRetriever` when the tile first shows, since the trash does not record it and the index has no video metadata yet (#384), and kept in memory by the file in the trash, which never changes while it is there, so a tile that scrolls back in opens no new retriever. Holding a video opens the same full size view with the same details, and plays it (§8, #388). The delete dialog says "files" instead of "images" when a video is among them. With nothing selected, a line above "Empty trash" says how much space the trash still takes ("The trash still takes up 1.3 GB."): a trashed video frees nothing until the retention ends, and people delete videos to get space now. When a page trashes more than 1 GB (10^9 bytes, as Android's formatter counts), the snackbar offers to free that space now, next to Undo, with a label that names the real figure, such as "Free 2.3 GB now". It deletes for good only the trash items that page made, not the whole trash, since the older items may still be waiting for the user to restore them. `moveToTrash` returns the item each file became, the page's `Decision` keeps them, and `Trash.purgeItems` deletes exactly those item folders: an item of the same path, size and mtime, such as a file a sync app put back that was trashed again, is never taken for one of them. It refuses a file that is not an item folder directly inside the `.cribrum-trash` of one of the volumes, compared canonically as a restore does, and skips such an entry so the rest of the batch still goes, so a look-alike folder elsewhere is never deleted. Like every delete for good it asks first (D6). The dialog lists what the page still has in the trash, since a restore or a delete on the trash screen may have taken some, and says how many files it deletes, how much it frees and that they cannot be restored. It does not open when nothing of the page is left. A confirm closes it, so a second tap deletes nothing more, and it takes the freed items out of the trash screen's selection. The snackbar and its Undo stay on screen while the dialog asks, so Cancel loses nothing, and a confirm ends the Undo, since the files are gone. Material's host would dismiss a long snackbar after its time whether a dialog is open or not, so this one is `Indefinite` and keeps its own time, Material's ten seconds as the accessibility settings lengthen them, counted from when it is on screen, not from when it is queued behind another snackbar: the time stops while the dialog asks, and starts again in full after a Cancel or a tap on "Free". When a restore or an Undo leaves files in the trash, the snackbar says "file" instead of "image" once a video is among them, and gives its own reason for an item refused because its path is on another volume, compared canonically as the restore does, so a path that reaches its volume through a symlink is not. "Largest videos" (#387) is where a page reaches 1 GB in practice: two videos of 1 GB are enough. A Motion Photo stays an image, and its video goes wherever the JPEG goes (see Motion Photos below).

A trashed image stays in the index, as `TRASHED`, while its file is in the trash: the scan does not find it, but does not forget it either. Its signals and review state are still there if it comes back. The index forgets it when the trash purges it, if the delete worked and the row is still `TRASHED`: a failed delete keeps the row, and so does a new file now at the same path. The scan starts with that purge, and takes the paths to forget from the same read of the trash: the items it read minus the ones it deleted, with no second listing (#352). A scan reconciles the two: a `TRASHED` row whose file is back on disk with no item in the trash, because someone moved it back by hand, becomes `UNREVIEWED` again, and one that is neither on disk nor in the trash is forgotten, as long as its volume was walked in full (§4). A file written at the path of a trashed image starts `UNREVIEWED` too. The scan judges only rows in the state they had when it began, so a review action that runs meanwhile, like a restore, keeps its result.

Compression (#173) rewrites a photo the user keeps, so it follows the same rule: the original goes to this trash. What it can rewrite, and how, was measured on a Galaxy Z Fold7 (One UI 9, SDK 37) in #283. Nothing was measured on Android 11 to 16 (SDK 30 to 36). Compression is Android only, so the lab has no counterpart.

- **Eligible photos.** A file is compressible when its bytes are an 8-bit baseline, extended or progressive JPEG (SOF0, SOF1 or SOF2, sample precision 8), it is not a Motion Photo, and nothing unknown follows the image (see Motion Photos). The phone had no SOF1 file, and Android does not decode 12-bit JPEG.
- **Ultra HDR.** A photo with a gain map is eligible only on API 34 and later, where `Bitmap` has the gain map API. Below that, `Bitmap.compress` writes a plain SDR JPEG. A file has a gain map when its headers have the `hdrgm` XMP or the ISO 21496-1 APP2 together with an MPF APP2. On SDK 37, `BitmapFactory` decodes the gain map, `inSampleSize` and `Bitmap.createScaledBitmap` keep it, and `Bitmap.compress` writes all three markers again (the `hdrgm` XMP, the ISO 21496-1 APP2 and the MPF APP2). The full pipeline ran on 2 photos. API 34 to 36 are untested, and so is whether the Gallery shows the result as HDR. The compressor refuses a photo whose headers show a gain map when the decoded or scaled bitmap has none, or when the headers of the copy it wrote do not show one, so an Ultra HDR photo never comes out as SDR. The second check covers an encoder that drops the gain map, which API 34 to 36 may do, untested. Ultra HDR photos are in because they are most of what is worth compressing: 195 of the 345 camera JPEGs on the test phone have a gain map, all 13 of 200 MP among them.
- **Motion Photos.** A miss destroys the video, and the test phone had no Motion Photo, so the rule is strict. A file is not eligible when any of these holds: its XMP has `MotionPhoto` or `MicroVideo` set to `1`, as an attribute or an element, under any namespace prefix; it ends in a Samsung SEF trailer (`SEFT` in the last four bytes) whose directory has a `MotionPhoto_Data` entry; its XMP `Container:Directory` lists an item whose semantic is neither `Primary` nor `GainMap`; or something other than an MPF secondary image or a SEF trailer follows the image. That last check covers other vendors' formats and Pixel portrait photos: with the SEF trailer cut off (from its first data entry to the end), the remaining bytes must end in an EOI (`FFD9`), and when an MPF lists secondary images, the last of them must end exactly there. An MPF whose entries do not parse fails this check, and a header walk that never reaches SOS (a broken segment, or more than 4,096 steps) makes the file unsupported, since a flag behind the break would go unread. The checks read the header segments, the file's last bytes and the SEF directory, never the image data. Bytes after the first EOI alone prove nothing: a gain map or a SEF trailer follows it in 196 and 330 of the 3,587 JPEGs on the test phone. On the first scan with these rules on the test phone, of 3,879 JPEGs, 3,865 were eligible (202 of them Ultra HDR), 12 were excluded for trailing data (1 of them Ultra HDR) and 2 were unsupported. The container and Motion Photo rules excluded none. Before the compress screen (#286) or the background job (#287) ships, the rule is checked on one Motion Photo taken on purpose.
- **What the result keeps.** The compressor copies every tag ExifInterface knows (154 tags in `androidx.exifinterface` 1.4.2, the GPS reference tags `GPSLatitudeRef`, `GPSLongitudeRef`, `GPSAltitudeRef`, `GPSSpeedRef`, `GPSImgDirectionRef` and `GPSDestBearingRef` among them, which `CompressorTest` pins, `GPSAltitudeRef` of 1 (below sea level) included), except the structural ones: the pixel size, the thumbnail and its offsets (with `Compression`, which in a JPEG's Exif describes the thumbnail), the tags that say how the original's pixels were encoded (`YCbCrSubSampling`, `BitsPerSample`, `PhotometricInterpretation`, `SamplesPerPixel`, `PlanarConfiguration`), which the new encode decides again, the TIFF strip and subfile tags and the raw formats' own tags (DNG, ORF and RW2), which a JPEG does not have, and the IFD pointers, which ExifInterface writes itself. It then sets the pixel size tags the original has to the new size. It finds the tags by reflection on ExifInterface's `TAG_` constants, which a ProGuard rule keeps in release builds, and refuses to compress if it finds fewer than 100. The maker note and tags ExifInterface does not know are not guaranteed. On 8 photos every copied tag read back the same, date taken, GPS, orientation, camera and lens included. The compressor keeps the XMP that `Bitmap.compress` writes, which for an Ultra HDR photo describes the new gain map, and does not copy the original's. One scratch copy got the same `DATE_TAKEN` from MediaStore as its original. That was not through the real swap, and Robolectric has no MediaProvider, so it is still to check on the phone after the real rename. The phone check on #285 found `GPSAltitudeRef` missing from the copies. ExifInterface 1.4.2 drops a tag at parse time when it is stored in a TIFF format other than the one it expects, and for this tag it expects BYTE or UNDEFINED: stored as ASCII, SHORT or LONG it reads as null, and so do its bytes and range. The phone stored it in one of those. So when ExifInterface returns null for it, the compressor reads tag 5 of the GPS IFD straight from the original's Exif APP1 (any of the five formats, either byte order) and writes 0 or 1 with `setAttribute`, with tests for SHORT, LONG, ASCII and big endian. The five other GPS reference tags (`GPSLatitudeRef`, `GPSLongitudeRef`, `GPSSpeedRef`, `GPSImgDirectionRef`, `GPSDestBearingRef`) expect ASCII (UNDEFINED passes too) and are dropped the same way when stored as BYTE, SHORT or LONG. No file seen does that, and a reference letter in a numeric format has no defined meaning, so they have no fallback.
- **What the result loses.** The compressed copy loses all of the original's XMP, except what `Bitmap.compress` writes for Ultra HDR. It also loses the Samsung SEF trailer, APP11 C2PA content credentials, any IPTC APP13, COM segments, the EXIF thumbnail, and any other data after the image end. The maintainer accepts that ([#173](https://github.com/Bert0ns/cribrum/issues/173#issuecomment-6591131814)), and the compress summary warns before confirming (#286). All of it stays only in the original, until the trash purges it. The warning says that the date, the place and the camera details are kept. It says what is lost: Samsung Gallery's Revert for an edited photo, re-blurring the background of a Live focus shot (its depth maps), the shooting mode info, the edits, ratings, keywords, captions and people tags that other apps saved in XMP, and C2PA content credentials, such as an "edited with AI" label. It also says that all of it comes back only by restoring the original from the Cribrum trash within the retention. The scan may store a flag per loss (re-edit data, depth map, XMP, C2PA) so the summary can name counts (#284).
- **Resolution.** The limits are 50,000,000 pixels for Balanced and 12,000,000 for Smallest. A photo already at or below the limit decodes at `inSampleSize` 1 and is not scaled. Otherwise the sample size is the largest power of two `s` with `ceil(w / s) × ceil(h / s) ≥ 0.99 × limit`. A test checks that rounding against a real decode. If the decoded bitmap is still above the limit, it is scaled to `floor(w' × f) × floor(h' × f)`, with `f = sqrt(limit / (w' × h'))` and `w' × h'` the decoded size. The 1% is there because half of a 200 MP photo is 49.9 MP. Without it, Balanced decodes all 200 MP: 1.0 GB and 3.3 s instead of 0.37 GB and 1.3 s. A megapixel is 10^6 pixels, so the Fold7's own 12 MP (4000 × 3000) and 48 MP photos keep their size at Smallest and Balanced. The table is #285's test:

  | Original | High quality | Balanced | Smallest |
  |---|---|---|---|
  | 16320 × 12240 (200 MP) | as is | `s` 2, 8160 × 6120 | `s` 4, 4080 × 3060, scaled to 4000 × 3000 |
  | 12000 × 9000 (108 MP) | as is | `s` 1, scaled to 8164 × 6123 | `s` 2, 6000 × 4500, scaled to 4000 × 3000 |
  | 8192 × 6144 (50.3 MP) | as is | `s` 1, scaled to 8164 × 6123 | `s` 2, 4096 × 3072, scaled to 4000 × 3000 |
  | 8000 × 6000 (48 MP) | as is | as is | `s` 2, 4000 × 3000 |
  | 4000 × 3000 (12 MP) | as is | as is | as is |

- **Memory.** Bitmap pixels live in native memory, so the 512 MB Java heap is not the limit. On the Fold7, High quality on a 200 MP photo peaked at 1.44 GB of native memory and 13 MB of Java heap. The peak was 1.8 times the decoded bitmap, for both the 200 MP and the 48 MP photos. Before each photo, the compressor estimates the peak as 2.5 times the decoded bitmap, `ceil(w / s) × ceil(h / s) × 4` bytes with the dimensions after sampling. It reads `ActivityManager.getMemoryInfo` then, not once per batch, and the photo fits when the estimate is at most `availMem − threshold`. The factor 2.5 leaves about 40% over a single phone's measurement. On the Fold7, with 2.7 GB free, High quality on 200 MP (an estimate of 2.0 GB) passes. The large decoded bitmap is recycled as soon as it is scaled. A photo that does not fit is refused at that level, with a message that the phone has too little free memory for it, and an `OutOfMemoryError` during the decode, the scale or the encode is a refusal too. High quality never falls back to a smaller size, because it promises the original resolution. On the Fold7's sensor sizes only High quality reaches gigabytes, but a 64 or 108 MP photo from another phone decodes at full size at Balanced too, then scales, and can hit the check. The free memory reading is injected, so tests can fake a low-memory phone.
- **The marker.** The marker is an APP15 segment: the identifier `cribrum` and a NUL byte, then plain ASCII `key=value` lines ending in `\n`, with no comment or date line (`Properties.store` adds both, so the writer does not use it). The keys are `version=1`, `level` (`high`, `balanced` or `smallest`) and `compressed_at` (ISO 8601, UTC). It takes about 70 bytes. A reader takes the first APP15 segment before SOS whose payload starts with `cribrum\0`, wherever it sits, and ignores any other APP15 (GraphicConverter's starts with `Q`). The compressor writes the marker last, after the EXIF save, then sets the mtime. It goes directly after the Exif APP1. With no Exif APP1 it goes directly after SOI, or after an APP0 JFIF that follows SOI. Either way it stays before the MPF APP2. MPF gives the gain map's offset from its own segment, so a segment between the MPF APP2 and the gain map image moves the gain map away from where MPF says it is. The size MPF records for the primary image goes stale by the length of the EXIF and the marker. Android's decoder ignores it and found the gain map, so #285 leaves it. ExifInterface saves keep the marker byte for byte (one moved it behind the XMP APP1, still before MPF), and BitmapFactory, ImageDecoder, ExifInterface and MediaStore ignore it. APP11 was the first candidate, but it belongs to JUMBF, which C2PA content credentials use, and the camera had already written C2PA into two photos. APP15 appears in none of the 3,587 JPEGs. Whether the Gallery, sharing or a cloud backup keeps the marker was not tested, and a file that loses it counts as not compressed (#173).
- **What the scan reads (#284).** The metadata phase (phase 2) reads these rules for every image whose header gave `image/jpeg`, as a second step after the metadata (`jpeg_headers`), and keeps how long it took as the `jpegHeaders` phase time. It stores the result in a `jpegs` table, one row per JPEG: the rules' version, the first rule the file fails in the order above (`unsupported`, `motion_photo`, `sef_motion_photo`, `container`, `trailing_data`) or `eligible`, whether it has a gain map, the estimated quality, the marker and its keys, and the four loss flags. The API 34 rule is applied when the list is read, not stored, so a phone updated to API 34 lists its Ultra HDR photos without a rescan. A changed file loses its row and is read again, a forgotten image loses it with the image, and a new rules version reads every JPEG again. A row the app wrote itself for a file it had just put at the path (`page_width` set, see The index) is read again too. Version 5 of the index adds the table and starts empty, so the first scan after the update reads every JPEG, as a fresh install does. The table is Android only, so `IndexSchemaTest` leaves it out of the comparison with the lab's schema. A write to it leaves the index version alone, as `not_images` does, since no ranking changes with it. The read keeps only the first 32 bytes of an Exif APP1 or an ICC APP2, whose contents no rule needs, since a camera's Exif with its thumbnail runs to about 64 kB, and it gives up on a SEF directory of more than 1,024 entries. On synthetic files of 200 kB (an Ultra HDR file with a SEF trailer), on the dev machine with the file in the page cache, a read takes about 0.26 ms. On the test phone, the first scan after the update read the headers of 3,879 JPEGs in 6,360 ms, about 1.6 ms a file, in a scan of 11.5 s. After each scan, the log tag `jpeg-status` gives the number of JPEGs per status, with and without a gain map, for the check on a real library. A failed read is a failure of the `metadata` step, and the next scan reads the file again. The re-edit flag is a SEF entry named `PhotoEditor_Re_Edit_Data` and the depth map flag one whose name starts with `DualShot_DepthMap`, the names found on the lab's copy of the test phone. XMP is any XMP APP1, and C2PA an APP11 whose payload starts with `JP`.
- **Quality and saving estimate (#284).** The quality is ImageMagick's estimate from the quantization tables. Its hash and sum tables are the standard tables scaled at each quality, so the app computes them. On JPEGs that Android's own encoder wrote at eight qualities from 30 to 100, it gives back the quality they were written at. The bytes a level would leave are the file's size, times the share of pixels the 1% rule keeps, times the size of a JPEG at the level's quality over its size at the file's estimated quality, from a curve measured in the lab with Pillow's libjpeg-turbo, times 0.934, the median ratio of Pillow's file at the original's estimated quality to the camera's own file. On 12 camera photos in the lab (6 of 12 MP, 3 of 48 MP, 3 of 200 MP, estimated at 92 to 96), the estimated saving was off by a median of 0 points of the original size at each level, and by 16 to 20 points at worst. For the 200 MP photos the estimate is within 5 points of what #283 saved on the phone. It is a lab calibration against Pillow, not against `Bitmap.compress`. A level whose estimate is not smaller than the file shows as saving nothing.
- **The swap.** The compressor writes the copy next to the original, on the same volume, as `.pending-cribrum-<random>.jpg`: the scan skips it (§4), and moving it to the original's path is a rename. It copies the EXIF, writes the marker, then sets the copy's mtime to the original's, before the swap. A rename keeps the mtime, so the copy has it from the moment it takes the path. Then `AppTrash.replaceWithCopy` moves the original to the trash, with the copy's size and mtime in its `origin.properties` (`compressed_size`, `compressed_mtime_ns`), renames the copy to the original's path without replacing any file, and tells MediaStore about the path. A copy that is refused or never takes the path is deleted by `AppTrash.discardCopy`, which deletes nothing but a file with exactly that name, outside the Cribrum trash, so the trash is still the only code that deletes. If the original changed since its scan, its record cannot be written, or anything throws before the swap, nothing moves and the copy is discarded. If the copy cannot be renamed, the original moves back. If that fails too, the original stays in the trash, where a restore puts it back: the compressor says so with its own reason, and marks the row `TRASHED` like any trashed image, so the next scan does not forget it. Once the copy has the path, the compressor reports it done even if the index update after it fails, since the next scan records the copy. A process killed between writing the copy and the swap leaves the hidden copy next to the original. The scan skips it, and the next batch discards it (see the batch job below). A process killed after the original went to the trash and before the copy took the path leaves the path empty, under a row that is not `TRASHED`. The scan keeps such a row while the row still holds the original's size and mtime and the trash holds that original with a compressed copy, so a restore finds the row with its review state, as after a finished swap. After a finished swap the row holds the copy's size and mtime, so a copy deleted in another app leaves the index like any gone file. A scan that cannot list the trash forgets no row, since any missing file could be such a half swap.
- **Restore.** Restoring an original whose record names a compressed copy first moves the file at its path to the trash, as an ordinary item, if it is still that copy (the same size and mtime), then moves the original back. A file at the path that is not the copy, such as one the Gallery edited, is left alone and the original stays in the trash, as with any restore onto a taken path. If the original cannot be moved back, the copy returns to the path. The copy's item is purged like any other, and purging the original's item leaves the copy where it is. Nothing is deleted outside the trash, so a compression can be undone for the whole retention (D6). A restore also marks a favourite again (see The favourite flag).
- **The index.** The index has one row per path (§4), so the copy takes over the original's row. `ImageIndex.record` sees the new size, keeps the review state, and drops the metadata, hashes, embedding, signals and `jpegs` row, which the next scan computes from the copy. The copy has the marker, and the compress page shows it as compressed as soon as the batch ends (#326): right after `record`, the compressor reads the copy's headers and resolution itself (`showBeforeScan`) and writes its `jpegs` row with the resolution in two columns of its own, `page_width` and `page_height` (version 6 of the index). The page takes the resolution from them while the row's metadata is empty. Only an eligible JPEG gets such a row, since the page lists no other. **The scan still reads the copy as a changed file.** What it uses to tell what to do is left alone: the metadata stays empty, so the metadata step reads the file; `jpegsToRead` lists every row with a `page_width`, so the header step reads it again and the scan's own row, with no `page_width`, replaces it; and the hashes, embedding and signals that `record` dropped are computed from the copy. Putting the resolution in the metadata instead would have skipped the metadata step, and the copy would have kept no camera, date or mime until it changed again. A test runs a scan after a compression and checks that every step reads the copy. Signals are not carried over: the content hash changes, and at Balanced and Smallest so does the resolution that picks the best copy of a group. A kept photo stays kept, and a new signal on the copy, such as a group role that changed, brings it back as for any edited file (§6.3). The original's trash item has no row. Restoring it puts the row back to the original's size, which drops the copy's `jpegs` row, and the row is analyzed again. The restore then writes the original's row the same way (`showBeforeScan`, from `Review.restore`, which Undo and the trash screen both use), so the page lists the original as compressible again before the scan. Any restore that changes its row does the same, which in practice is a compressed original or a file the index had forgotten. It keeps the review state it had, because a restore is a keep decision and the row still holds the original's kept signals and detectors, which a changed size does not drop. This is the one restore onto a row that is not `TRASHED`. Any other restore onto a row that changed since the trash took the file still comes back unreviewed (`Review.restore`). Purging either item never forgets the row while the copy is at the path, since the row is not `TRASHED`. When the user trashes the copy too, both items hold the path and the row is `TRASHED`, so a purge forgets the row only when no item left in the trash holds its path (`Trash.unheldPaths`, used by the purge from the trash screen and by the scan's purge of the expired items). No migration.
- **The favourite flag (#288).** MediaStore keeps `IS_FAVORITE` on a row, not on the file. Where a compression or a restore keeps it:
  - *The swap loses it.* The copy is a new row (new `_id` and `date_added`, #285), so the gallery's heart is gone.
  - *Undo on the test phone kept it.* The original goes to `.cribrum-trash` and back by rename, and the phone brought its old row back (#285). The code cannot rely on that: a MediaStore scan that drops the row while the file sits in a `.nomedia` folder would leave the restored file with a new row and no mark, and nothing in the app can tell which phones do that. So the trash writes `favorite=true` into the item of every file it moves (the swap's original and an ordinary trashing alike) when MediaStore flags its path at that moment. The query names the paths it asks about (`DATA IN (...) AND IS_FAVORITE = 1`, 500 at a time): the paths of a move call, or the one path of a swap, never every favourite of the library for each photo. A query that fails counts as none, so it never stops a move. A copy that a restore puts in the trash is recorded the same way.
  - *The batch.* The swap reports whether the original was a favourite, and the batch keeps the paths of the compressed ones (`BatchResult.favorites`). After the result is published, the job asks for the mark on those paths in one request. The request is dropped, when it is queued and again when it is about to launch, if that result is no longer the one on show (the user undid the batch, or started another): the copies are in the trash then. A photo whose compression was refused or stopped still has its own row and mark.
  - *A restore* (Undo of a batch, the trash screen, Undo of a review) asks for the mark on the restored files that were favourites, after the restore. In both cases the request runs on the app's own scope after the restore or the batch has returned, so the restore, the Undo and the scan lock never wait for it: it waits for MediaStore to scan the paths (at most 10 s, and after that it asks about the rows that exist) and then asks about the rows that are not favourites yet. So when the old row came back with its mark, nothing is asked and no dialog shows; a path with no row (a `.nomedia` folder, which MediaStore does not index) has no mark to lose and is not asked.
  - *One system request.* It is `MediaStore.createFavoriteRequest` with all the rows of the batch or the restore. It needs an Activity, so the data layer queues it in `FavoriteRequests` and `FavoriteRequestHost`, in `MainActivity`, launches the queued requests one at a time while the activity is started, on whichever screen is open. It waits for the screen to be free before it takes a request off the queue, so a rotation or Home during the wait loses nothing. A rotation brings the answer to the new activity. An activity that is finished for good (not rotating) drops the request on screen, since no answer will come, so later requests are not blocked until the process dies. The Compress page does not launch it: a restore from the trash screen needs the same launcher, and one host serves both. A batch that ends while the app is in the background or closed has its request wait in memory, and it goes out the next time the activity starts, which is usually on the Compress page where the user left it. The result and the Undo are on that page already. A killed process drops the queued request, and the copies stay without the mark; the originals in the trash still say `favorite=true`, so restoring one asks again.
  - *A decline.* The compress result says how many photos lost their favourite flag (`BatchState.Finished.favoritesLost`, a plural line under the counts). A system dialog that cannot open counts as a decline. A declined request after a restore says nothing, since the user has just chosen. Photos the user declined can be marked again in the gallery by hand.
  - The system probably grants a favourite request without a dialog, for every app: in AOSP's MediaProvider the request shows a translucent activity that returns at once. The code does not depend on it: a granted request is a granted request, and a dialog the user declines is a decline. It was not checked on the phone (§11).
- **One at a time, never during a scan.** Whatever runs the compressor (the compress screen, #286, and the background job, #287) runs one compression at a time, and never while a scan runs. A scan records files in batches, and a batch that read the original's size before the swap would write that size back over the copy's row. Two compressions at once would each read the free memory before either has decoded, so both would pass the check that only one fits. The compressor does not enforce this itself: the batch job does, and the compress screen runs every compression through it.
- **The batch job (#287).** `CompressBatch.start` takes a list of indexed paths and a level, and a WorkManager job (`CompressWorker`, unique work `compress`) compresses them one at a time, in the order given, in the foreground with a notification: "Compressing 3 of 12", the bytes saved so far, and a Cancel action. From API 35 the job runs as a `mediaProcessing` foreground service, which has a time budget of its own, so a long batch or a long pause for the heat does not use up the `dataSync` budget the scan needs (§4). Below API 35 it runs as `dataSync`, which has no budget there. `CompressBatch.state` is a `StateFlow` for the compress page: idle, waiting for a scan, running (photos done of the total, the saving so far, paused for the heat) and finished, with the result. One batch at a time: `start` refuses a second while one waits or runs. Each path is checked against the size and mtime the index holds when the batch starts, so a photo that changed since its scan is refused, and so is a path the index does not hold. Cancel lets the photo in progress finish, since the compressor cannot be interrupted, and stops before the next one: the photos done so far stay compressed and their originals stay in the trash. A cancel or a stop by the system takes the job out of the foreground while that photo finishes, so the system can kill the process in the middle of it. That leaves either a hidden copy, which the next batch discards, or a half swap, whose row the scan keeps (see the swap above). The result says how many photos were compressed, how many each refusal stopped, how many the batch did not reach, the real saving (the originals' size minus the copies'), and the originals the batch moved to the trash, those of a swap that failed halfway included. Undo for the whole batch (`CompressBatch.undo`) restores those originals through `Review.restore`, which puts each copy in the trash in its place, so nothing is deleted. It takes the same lock, so it waits while a scan or a batch runs: a restore rewrites rows a scan may be recording. The request and the result live only in memory: a process killed mid-batch drops the rest of the batch, WorkManager's rerun finds nothing to do, and the Undo is gone with the result, while the originals stay in the trash to restore from the trash screen.
- **The batch against the scan.** The job holds the scan's lock (`IndexWorker.running`) for the whole batch. A batch asked for while a scan runs waits for it, shows "Waiting for the scan to finish", and starts when it ends. A scan that starts while a batch waits or runs returns without scanning, as a nightly run does when "Scan now" is running: the nightly one is pinned to the next night (§4), and a "Scan now" is dropped, so Clean does not offer it then: its "Scan now" gives way to a line saying a compression runs. When both are asked at once, the batch wins: `start` marks the batch as waiting or running before its worker starts, and a scan checks that mark after it took the lock, so a scan that has not yet taken the lock and passed the check counts as not started. The batch goes first because the user asked for it and watches its notification, while the nightly scan comes back the next night, and a scan after a batch reads the copies, so the compress page shows them as compressed sooner. Before the first photo, holding the lock, the job discards the copies a killed compression left (`.pending-cribrum-<uuid>.jpg`, through `AppTrash.discardCopy`) in every folder that holds an indexed image, since no compression can be running then.
- **Heat.** Before each photo the job reads the thermal status and the headroom, as the scan's heat line does (§4), and while the level is severe it waits, reading again every 10 seconds, and the notification says "Paused while the phone cools down". A photo in progress is never stopped for the heat. Nothing was measured on the phone yet: how hot a batch of 200 MP photos makes it, and how long the pauses take.
- **Preview.** `Compressor.preview` runs the same decode, scale, encode, gain map checks and EXIF copy into a file the caller names, without the marker or the swap, and returns the same refusals, `NOT_SMALLER` included when the file is not smaller. It goes through the same memory check as a compression (2.5 times the decoded bitmap against `availMem − threshold`). The compress summary (§8) calls it for up to three photos, one after the other, each into its own file. It takes the compressor's own lock, so two previews do not overlap. Unlike a compression it is cancellable, since a closed summary should not leave a 200 MP decode holding the lock: it checks for cancellation between the decode, the scale and the encode (the bitmap calls themselves cannot be interrupted), recycles its bitmaps, and deletes the output through `AppTrash.discardCopy` when it refuses, fails or is cancelled, so the output is named by `copyFileFor`. The summary only opens when no batch of the screen waits or runs: the preview does not take the "never during a scan" rule's lock, because it writes nothing a scan reads, but it uses the memory of one photo at a time, and a batch is using one at the same time.
- **Refusals.** The compressor returns the copy, or one reason the compress screen (#286) words: the result is not smaller, the phone has too little free memory (an `OutOfMemoryError` included), the bitmap or the copy lost its gain map, anything else failed (a file that could not be read, written or swapped, or that changed since its scan), or the original was left in the trash. The original stays at its path in every case but one, a swap that failed halfway and could not move it back, which has its own reason: the original is in the Cribrum trash.
- **Tests for #285.** Besides the table above: all three Ultra HDR markers (`hdrgm` XMP, ISO 21496-1 APP2 and MPF APP2) survive the whole pipeline, encode, EXIF save and marker, and the gain map still decodes. A photo whose bitmap lost its gain map is refused. A faked low-memory reading refuses High quality on a large photo. Robolectric's native graphics decode no gain map and write none, so the unit tests check the bytes: the three markers survive the EXIF save and the marker, and the MPF still points at the gain map image. The encode, and the decode of the result's gain map, stay with the phone (#283 checked them on SDK 37). Every Ultra HDR photo loses its gain map in Robolectric's decoder, which is how the refusal is tested. The tests also check that MediaStore is told about the path after the rename, when the file there has the original's date taken and mtime. `DATE_TAKEN` itself needs the phone.

## 10. Python lab

Goal: prove that the detectors work on real data before writing the app.

1. **Collect:** copy the device's images to a local folder (`adb pull`, or a USB file transfer), messaging-app folders included. Image data is never committed.
2. **Detect:** implement the detectors behind the same interfaces as §7.
3. **Label:** a keyboard-driven labeling tool (`k` = keep, `d` = delete). A label carries no category: the labeler can tell what to keep, but not which detector should catch it, and asking for one turned out slow and error-prone. MobileCLIP clusters similar images so a whole cluster can be labeled at once. Target: 500–1,000 labeled images.
4. **Measure:** **recall** first, then the number of candidates it costs. The target is 95% recall on deletable images, measured for the whole library, not for the labeled sample. The sample is stratified: half of it is candidates, spread over the categories, and half is images no detector flagged, while 88% of the library were candidates when the first labels were drawn. It over-represents the images that are hardest to catch, so its recall reads lower than the library's. The evaluate report prints both. For the library, it weights each label by the size of its stratum in the index divided by the number of labels in that stratum. Each label records its stratum from now on (`candidate` or `unflagged`, `labels.sqlite` gets the column when it is opened). The 1,200 labels made before that have none, so the report places them by whether the thresholds in use when they were sampled made their image a candidate (`SAMPLING_THRESHOLDS`, the values before this change). That is an approximation, and the report says how many labels it applies to.

    | Thresholds | Sample recall (716 deletes) | Library recall | Kept images flagged (of 484) | Candidates (of 10,220) |
    |---|---|---|---|---|
    | Before | 79% (567) | 94% | 210 | 9,010 |
    | Now | 86% (615) | 96% | 219 | 9,171 |
    | Cheapest found for 95% on the sample | 96% (689) | 97% | 342 | 9,751 |

    On the sample, the 90% to 95% steps catch the last images only through `FORWARDED` at 0.45, which flags every messaging-app image and makes 95% of the library candidates. Measured on the library, the target is met with the thresholds in `ranker.py` and `Ranker.kt`. Stickers (6,306 images, 62% of the library) are always candidates, so they are more than two thirds of the candidates at any recall.

    **How the thresholds were picked.** The evaluate report prints, for each category and threshold, the labeled deletes and keeps the category flags and the ones it adds to the candidates the other categories already make. A threshold is lowered only when the images it adds to the whole candidate set are clearly more often deletes than keeps. Steps that add a handful of images are noise. The values are the maintainer's choice, read from that table:

    | Step | Deletes added | Keeps added | Candidates added |
    |---|---|---|---|
    | `DOCUMENT` 0.5 to 0.2 (applied) | 48 | 9 | 158 |
    | `DOCUMENT` 0.2 to 0.1 | 17 | 11 | 111 |
    | `BLURRY` 0.4 to 0.2 | 6 | 7 | 34 |
    | `NEAR_DUPLICATE` 0.5 to 0.3 | 3 | 6 | 33 |
    | `BAD_EXPOSURE` 0.5 to 0.4 (applied) | 0 | 0 | 0 |
    | `BAD_EXPOSURE` 0.5 to 0.1 | 1 | 0 | 5 |

    Only `DOCUMENT` clears the rule. `BAD_EXPOSURE` at 0.4 changes nothing on these labels. Every other category stays at 0.5 (`BLURRY` at 0.4). `BURST` has a small list (63 images, 10 deletes and 28 keeps), but recall comes before precision and it costs few reviews. `FORWARDED` at 0.4 would flag every messaging-app image, for 301 more deletes and 224 more keeps over 2,198 more images outside sticker folders, about the sample's base rate, so the extra images tell nothing.

    Lower thresholds also move images up the review order: the chance that a labeled delete comes before a labeled keep goes from 0.768 to 0.785.

    **Same labels.** The thresholds were picked on the same labels they are measured on. A bootstrap over the labels gives 83% to 88% for the sample recall and 95.2% to 96.6% for the library recall (95% intervals). A review of the first set of thresholds tried, which moved more thresholds and reached 90% on the sample, held out half of the labels in 20 random splits: 89.5% recall on average and 83% at worst. New labels, drawn with the recorded strata, are the check.

    The 101 deletes in the sample that no detector flags are 95 in messaging-app folders and 6 in camera folders. For all 95 of the messaging ones the closest category is `FORWARDED`. They are photos in a messaging folder that the zero-shot prompts do not read as memes or greetings, so nothing in the signals tells them from the 108 kept messaging images that are flagged. What to chase next is a signal for received photos nobody kept, not a different threshold.

    Recall of the categories on the 716 deletes, with the deletes no other category flags in brackets: `FORWARDED` 45% (32), `DOCUMENT` 43% (81), `STICKER` 33% (30), `SCREENSHOT` 15% (29), `NEAR_DUPLICATE` 16% (14), `BLURRY` 14% (6), `BAD_EXPOSURE` 12% (1), `BURST` 1% (4), `EXACT_DUPLICATE` 0.3% (0). Most deletable images are flagged by several categories, so a category's recall alone is not what it adds. The report prints both columns, so a re-run refreshes them. These figures come from before stickers stopped running blur and exposure (§5, #375). The report counts reasons, not lists, so since then its `blurry` and `bad_exposure` rows count no sticker, and a sticker delete that was also blurry or badly exposed counts under `sticker` alone. On the labels of #359 that took `blurry` from 567 candidates to 94 and `bad_exposure` from 192 to 118, the stickers that left were never listed in those categories, and no delete lost the one category that flagged it.
5. **Freeze:** export golden fixtures (sample images with expected signals) for the Kotlin implementation's tests. The fixture images are synthetic, generated from fixed seeds (`fixtures/`), never personal photos.

**Videos.** The lab mirrors the media type and the walk (#383) in `model.py`, `sources.py`, `index.py` and `pipeline.py`, the metadata (#384) in `metadata.py`, and the frames (#393) in `frames.py`. It mirrors the video detectors too: `EXACT_DUPLICATE`, `FORWARDED`, `TAKES` and, from the stored frame measures (`frame_measures.py`), `BLURRY`, `BAD_EXPOSURE` and `FACES` (#394). Its `evaluate` report for videos uses `VIDEO_THRESHOLDS` over the photos' thresholds, and the thresholds it suggests are for `VIDEO_THRESHOLDS`. It reads videos with [PyAV](https://pypi.org/project/av/). PyAV's binary wheels on PyPI bundle FFmpeg, so the lab needs no FFmpeg on the system. That was checked on 2026-11-14 against PyAV 19.0.2, released on 2026-10-21: its Linux x86-64 wheel carries FFmpeg 9.0.2 in `av.libs`, with the H.264, HEVC, VP9 and AV1 decoders and the MP4, MOV, 3GP, Matroska and WebM demuxers. It needs Python 3.12 or later, as the lab does. The Videos list, the trash screen and the storage map stay Android only. #390 pulls the videos from the phone and labels them before any video detector is tuned, since the thresholds come from the lab (D2). The video fixtures in `fixtures/videos/` are short synthetic videos made with ffmpeg by `lab/scripts/make_video_fixtures.py`, a few KB each, with the values both sides must read (#384), never personal videos.

**The video sample (#390).** `lab/scripts/pull_device_videos.py` copies videos from the phone into `lab/data/device/`, beside the images, with the device's folders and modification times, and only reads the phone. The maintainer's phone holds 51 GB of camera video and 8.6 GB in messaging folders (#172), and the dev machine had 35 GB free on the drive that holds WSL, so the sample is drawn on the phone side, by folder, and a run must say how many videos it takes (`--sample N` or `--all`): `--sample N` takes N videos from each folder it is given, ordered by a hash of the path, so a larger N keeps the videos a smaller one took. Labelling takes the maintainer's time, so the first sample is small: 20 camera videos from `DCIM/Camera` and 30 from WhatsApp's `WhatsApp Video`, `Sent` included, about 4.5 GB by the averages of #172. The messaging folders can follow in full. `label --videos` labels them one at a time, playing each one, into the same `labels.sqlite`, keyed by content hash and with the stratum of an image label. Each label records its media type (`labels.sqlite` gets the column when it is opened, and older labels are images), so a video that left the index stays in the video report. The first 49 video labels were taken before any video detector existed, so each one is `unflagged`. The evaluate report adds the same report for the videos alone, after the images'. Its library recall covers the videos in the index, which are the pulled sample, not the phone's: the sample takes as many videos from a folder of 146 as from one of 1,178, so a recall for the phone weights each folder by its count in #172.

## 11. Future work and open questions

- **Cloud classifiers:** a `Detector` implementation that calls a vision model API. It should be opt-in, send only downscaled thumbnails, and exclude images with faces by default.
- **Cloud libraries:** a new `MediaSource`. Since 2025 the Google Photos Library API no longer gives third-party apps read access to a user's whole library, and it never supported deletion. Cleaning Google Photos may need a different approach.
- **Play Store:** "All files access" is granted only to specific app categories. Deep scan might have to become an optional feature.
- **Desktop and iOS:** reachable through Kotlin Multiplatform / Compose Multiplatform.
- **Learning from decisions:** adjust per-category thresholds from the user's keep/trash history.
- **Recall level as a setting:** the user picks how many of the deletable images the candidates should catch, trading a longer review for fewer misses. The lab would export one set of thresholds per level instead of one. The settings screen already has one slider per category that has a graded score (§8), so this would be a simpler control on top of it, not a replacement.
- **Keeping Samsung's trailer in a compressed photo:** copy the SEF trailer of the original into the new file, so the Gallery's Revert, Live focus re-blur and the capture info survive a compression (§9). It needs a check that the Gallery still reads it and that entries such as the re-edit data still fit the new pixels, so it is its own issue.
- **The favourite flag on the phone (#288), still to check:** (1) whether the Samsung Gallery shows a compressed photo in the same albums as before. The albums are the Gallery's own data and the code cannot know it, so the compress summary has no warning for it. Look at an album that holds a compressed photo, before and after a batch: is the copy in it, and does the album's photo count change? (2) Whether `createFavoriteRequest` shows a dialog on the phone, or the system grants it without one as AOSP suggests. (3) Whether an Undo keeps the mark of the old row after a MediaStore scan or a reboot between the batch and the Undo. (4) A request left in the queue by a killed process is not asked again; a persisted list would fix that.
- **Profiling the app:** profile a full first scan and the review screens on a real phone (Android Studio profiler, Macrobenchmark) and fix the hot spots. §5 already records the per-image cost of MobileCLIP and text coverage. The first target is the total time of a first scan of 10,000 photos.
